# interview-room

候选人面试间的服务端。页面在 `web/apps/candidate`，协议在 `docs/architecture/api.md` 的「面试间协议」。

## 现在有什么

| 接口 | 做什么 |
| --- | --- |
| `GET`、`POST /api/v1/interviews/{id}/invites` | HR 查看、生成面试链接 |
| `DELETE /api/v1/interviews/{id}/invites/{invite_id}` | HR 撤销链接 |
| `GET /api/v1/interviews/{id}/events` | HR 查看过程事件 |
| `GET /api/v1/interviews/{id}/recordings`、`GET /api/v1/recordings/{id}/media` | HR 看录制列表、回放 |
| `GET /api/v1/room/session` | 候选人打开链接后拿会话信息 |
| `POST /api/v1/room/consent` | 候选人确认同意事项 |
| `POST /api/v1/room/device-check` | 页面上报设备检测结果 |
| `POST /api/v1/room/uplink-probe` | 页面测上行网速时往这里发一段字节，收完就丢 |
| `POST /api/v1/room/start` | 开始面试（或者刷新后接着面），返回该播的那一句 |
| `POST /api/v1/room/advance` | 页面每播完一句、候选人每答完一段调一次，返回下一步 |
| `GET /api/v1/room/utterances/{key}/audio` | 面试官语音 |
| `POST /api/v1/room/finish` | 候选人中途结束面试 |
| `POST /api/v1/room/events` | 页面批量上报过程事件 |
| `PUT /api/v1/room/recordings/{track}/{segment}` 和它下面的 `chunks`、`complete` | 页面分片上传录像 |

面试有两种进行方式：逐题（题目和追问都是提前写好、提前合成的）和实时对话（面试官现场接话）。两种用的是同一套接口，页面不用分两套写。

## 面试怎么往下走

代码在 `src/conduct.rs`。下一步说什么由 `interview_engine::room` 决定，面试间做它周围的事：

- **状态**存在 `interviews.runtime_state`（引擎的 `RoomState`）。每次改动都在锁住这场面试那一行的事务里做，同一个请求来两遍不会把面试推进两次。`state.last` 就是刷新之后该重播的那一句，`GET /room/session` 的 `resume` 和再调一次 `start` 给的都是它。
- **对话记录**写进 `interview_turns`。每一拍占两个序号：面试官的话是 `2×seq−1`，候选人的回答是 `2×seq`，重复上报不会记两遍。候选人的文字先空着：提问环节的回答在判断时填上现场转写的结果（`transcript_source` 是 `live`），面试结束后整段重新转写时再补全。
- **判断回答**：候选人开口答完一段，先把过渡语（「好的，谢谢」）发给页面播，同时在后台判断这段回答要不要追问。页面报告过渡语播完时判断还没好，这次请求就等它。判断最多等 `settle_timeout_sec`（默认 20 秒），等不到或者模型出错就不判断，按顺序问下一题，不让候选人干等。
- 判断要有这段回答的文字，由现场转写给（见下面的「现场转写」）。拿不到文字或者没配大模型时不判断：面试照常问完所有题，只是没有追问，也不会因为答得差提前结束。
- **面试官语音**只给当前这一句、服务端让提前取的那几句和已经播过的。还没问到的题取不到，候选人没法提前听题。没合成出语音的句子 `audio_url` 是空的，页面只显示文字。
- **结束**：引擎说结束时，同一个事务里把状态改成 `completed`、记下原因，并排一个 `interview.finalize` 任务（转写和出报告由它接手）。候选人中途点了结束是 `abandoned`，原因 `candidate_left`。
- **候选人不回来了**：开始面试时排一个 `room.watchdog` 任务。它看最近一次动静（状态变化、录像分片、过程事件），超过 `AI_INTERVIEW_ROOM_ABANDON_MINUTES`（默认 15 分钟）没有动静就结束面试，状态 `abandoned`，原因 `connection_lost`；还有动静就约好下次再看。结束语已经发出去的不算中途离开，记成正常结束。
- 页面报上来的时刻不能比服务端的时钟快 5 秒以上，超出的按服务端的算。

## 实时对话

代码在 `src/realtime.rs`。面试配置的 `mode` 是 `conversational`，而且大模型、语音合成都接上了、语音识别能用，这场面试就按实时对话进行；少一样就按逐题进行（开始时定下来，中途不变）。怎么接话由 `interview_engine::live` 决定。

一轮是这样走的：

1. 页面判断候选人说完了（实时对话里停 `AI_INTERVIEW_ROOM_REALTIME_SILENCE_SEC` 秒，默认 2 秒；停顿时先问过服务端的按下面「候选人停顿时先想」算），立刻把手头的录像传上来，调 `advance`。
2. 服务端记下这段回答，在后台开始「想」：用现场转写拿到这段话的文字，交给引擎。
3. 引擎边想边出结果。提前合成好的句子（过渡语、下一题）直接排进队列；现场生成的追问和回应按句子合成（`Deps::with_voice` 接进来的 `LiveVoice`，用这场面试选的音色），合成好一句排一句。
4. `advance` 在队列里有句子时马上返回，没有就等（最多 30 秒，到时候返回 503，页面重试）。

候选人停顿时先想（`POST /room/pause-check`）：

等满 2 秒静音才开始想，候选人每次都要多等这 2 秒。所以声音一停下 `AI_INTERVIEW_ROOM_REALTIME_PAUSE_CHECK_MS`（默认 0.5 秒），页面就先传一片录像、问一次服务端「这段话说完了吗」。服务端转写到停顿为止的这半段话，用引擎的 `respond_with(paused: true)` 让模型看：

- 模型觉得**说完了**：它同时给出了怎么接，现场生成的话这时就开始合成。页面收到 `done`，这次停顿静音满 `AI_INTERVIEW_ROOM_REALTIME_DONE_SILENCE_MS`（默认 1 秒）就调 `advance`。`advance` 报上来的回答和问的时候是同一段（起止时刻相同），服务端直接用备好的结果：文字不用再转写，模型不用再问，句子已经合成好或者正在合成。
- 模型觉得**没说完**（半句话、在想）：页面收到 `wait`，这次停顿等到 `AI_INTERVIEW_ROOM_REALTIME_WAIT_SILENCE_MS`（默认 3 秒）才算说完，免得把候选人的话掐断。到时候再照常问一遍模型。
- 模型出错、转写没赶上、4 秒内没有结论：`unknown`，按 2 秒算，和没有这个功能时一样。

候选人接着说了，备好的结果就作废（`advance` 报上来的起止时刻对不上），已经合成的句子不会发出去，下一次停顿重新问。一段回答最多问 8 次。备的时候不写对话记录、不动面试进度，只记模型用量；被采用时才把转写的文字、模型的结论和句子写进去，和照常想一轮写的东西一样。备着的结果记在 `Hub` 里（`Ahead`），和「正在想」一样只在进程内存里。

代价是每次停顿多调一次模型（输入一千多个 token，一场面试多几分钱），以及候选人接着说时白合成的那一两句。

候选人插话（`barge_in`）：

面试官说话时候选人开口，面试官要停下来听。判断分两步，页面一步，服务端一步：

1. 页面播面试官的一句话时一直看着麦克风的音量。一听出候选人出声（约 0.15 秒）就先停下不播。之后声音再持续 `AI_INTERVIEW_ROOM_REALTIME_BARGE_IN_MS`（默认 0.4 秒）算插话：不再往下播，照常听候选人说完，`advance` 时带上这一句播到了哪（`interrupted_played_ms`）。不到这么久就没声了的（咳嗽、嗯一声），从停下的地方往回退 0.25 秒接着播。一句里最多这样停 2 次，页面连着 4 次白停之后这场面试就不再停。
2. 服务端收到插话，把后面排着没播的句子收起来（`Cut`），转写候选人的话，把「面试官的话断在哪、哪些没说出来」交给引擎（`TurnContext::interrupted`），模型看得到这样的记录：`面试官：第 1【说到这里被候选人打断，没说出来的部分：题的题目】`。接着怎么办由模型定：回应候选人、把没说完的重说一遍，或者照常往下。
3. 没听出话来的不算插话（`nothing_said`）：没转写出字、只有一个字，或者转写出来的就是面试官那一句里的字。录像里的声音是麦克风和面试官的声音混在一起的，页面停下之前的那一小段会混进候选人这段话的开头；扬声器的声音漏进麦克风时，转写出来的也是面试官自己的话。这种情况把被打断的那一句重新发一遍（新的一拍），后面排着的句子照旧，对话记录里不留这一段。出了 2 回（`MAX_FALSE_CUTS`），这场面试之后就不再让插话。

插话要留意的地方：

- 结束语不让打断。被打断的是上一轮先放出来的一句（那一轮还没想完）时，`advance` 等那一轮想完再处理。
- 现场生成的一段话拆成几拍，引擎要的「播了多少毫秒」是从这段话的第一句算起的，所以每一拍记着前面几句一共多长（`RtBeat::lead_ms`）。
- 候选人这段话的起点比页面听出开口的时刻早 0.2 秒（`BARGE_IN_LEAD_MS`）：页面要听 0.15 秒才敢说有人出声，不往前挪会丢掉第一个字。
- 被打断的那一句在对话记录里还是整句的文字，时间是实际播的那一段。
- 扬声器外放时回声消除得干不干净，只有真机上才知道（issue #15）。回声最多让面试官的话卡一两下：页面一停播回声就没了，撑不到 0.4 秒；真被当成了插话，服务端转写出来的是面试官自己的话，也会被上面第 3 条挡住。

要留意的地方：

- **一句一拍**。「好的，我了解了。那个方案里你本人负责哪一块？」是两拍：「好的，我了解了。」先播，问句在它播的时候合成。两拍的 `key` 相同（`q1.p1`），语音地址用 `?part=N` 区分。最后一拍要等引擎说这一轮的话都给出来了才发（引擎的 `Done` 事件），因为它播完是听回答还是结束面试，那时候才知道。换题时引擎这之后还要写上一道题的概括，面试间不等它。
- **同一场面试同时只有一个任务在想**，记在进程内存里（`Hub`）。进度每排进一句写一次库，所以进程重启后排好的句子还在，没想完的那一轮在页面重试时重新想。一场面试要由同一个进程服务到底。
- **哪里出错都不卡住面试**：没转写出文字，告诉模型「这一段没有听清」；模型出错或超时，按顺序问下一题；合成失败或超过 20 秒，这一句只显示文字。
- 现场生成的每段话在 `interview_utterances` 里登记一行（`source = 'live'`），面试后整理记录和出报告按 key 找得到。它的语音只供面试中播放。

延迟（候选人说完最后一个字到面试官开口）：

| --- | --- | --- |
| 候选人说完最后一个字到面试官开口 | 3.3 到 3.5 秒 | 3.8 到 3.9 秒 |

同一天后来改了两处，又各跑了一场：页面的静音改成从声音真正停下的那一刻算起（以前要多等 VAD 确认停止的 0.4 秒），中位数从 3.6 秒降到 3.2 秒，p95 3.7 秒；引擎说这一轮的话都给出来了就放出最后一句，换题的轮次里最后一句早 0.1 到 0.5 秒放出，不影响开口的时间。

再后来加了「候选人停顿时先想」，同样的办法又跑了一场（12 轮，12 次停顿模型都判断说完了，备好的回应 12 次都用上了）：

| | 中位数 | p95 |
| --- | --- | --- |
| 候选人说完最后一个字到面试官开口（停顿时先想） | 1.7 秒 | 2.3 秒 |

这 1.7 秒里：声音停下 0.5 秒去问（其中 0.4 秒和 VAD 的确认重叠），等这半段话转写出来 0.3 到 0.6 秒，模型判断 0.8 到 1.5 秒；结论回来时静音已经超过 1 秒，页面当场上报，服务端 0.1 到 0.6 秒内把备好的第一句发回来。现在卡在转写加模型判断这一秒多上，再把 `DONE_SILENCE_MS` 调短没有用。

又跑了一场话说到一半停下来的（回答的录音里，半句话后面插了 2.6 秒的空白再接着说）：11 次停顿里模型 4 次判断没说完、7 次判断说完了，都判断对了。判断说完了的 7 轮照样是 1.3 到 1.9 秒开口。判断没说完的 4 次里，2 次候选人接着说的话接上了，没有被掐断；1 次转写慢了，结论回来时已经过了 2 秒，这段话还是按老办法在 2 秒时算说完了；1 次候选人重新开口的那一下正好卡在 3 秒的边上，没赶上。后两次是 3.7 到 3.8 秒开口（多等的 1 秒加上照常想一轮），这是「没说完」判断的代价：候选人其实说完了的话，要比原来多等一秒。结论一般在声音停下 1.7 到 1.9 秒时回来，离 2 秒很近，转写或者模型慢一点就赶不上，赶不上就和没有这个功能时一样。

下面说的是加这个功能之前的构成。表里的数字是从页面听出候选人停止说话算起的，声音其实在那之前 0.4 秒就停了。这里面 2 秒是等静音（判断「说完了」），改了之后其中 0.4 秒和 VAD 的确认重叠。剩下的一秒多：转写 0 到 0.4 秒（文字是边传边识别的，答完时基本已经有了），模型决定怎么接 0.7 到 1.2 秒，其余是上传最后一片录像和取语音。

**这些数字不含语音合成**：云端没有真的合成引擎，用的是瞬间完成的测试音。提前合成好的句子（过渡语、下一题）接上真引擎也不受影响，现场生成的追问和回应要加上合成的时间。IndexTTS 2 在 Mac 上合成一句两三个字的接话约 2 秒，一句 25 个字以内的问句约 3.5 秒（语音线 2026-11-13 实测，见 `tts/worker/README.md`）。

为了不让候选人干等这几秒，做了三件事：

- 引擎规定每次现场开口的第一句是一句固定的接话，从 `interview_engine::openers(语言)` 的清单里选（中文、英文各八句，每句念出来两秒左右，具体哪几句见 `crates/interview-engine/docs/realtime.md` 的「第一句是固定的接话」），模型写了别的会被换成清单里的。接话后面的长句在逗号处断开。合成好一句放一句，候选人先听到接话，问句在它播的时候接着合成。
- 面试一开始，就在后台把这份清单用这场的音色合成一遍（`AI_INTERVIEW_ROOM_REALTIME_WARM_UP`，默认开）。语音合成按音色和文字有缓存，之后现场说到这几句不用等合成，所以第一句都是现成的。同一个音色以前说过的，这一步只是八次缓存命中。
- 候选人停顿时先想的那一轮，现场的话当时就开始合成，不等页面上报。

语音线在 Mac 上接真的 IndexTTS 2（克隆音色）跑过整场实时对话（2026-11-13，#154，表在 `tts/worker/README.md`）：

| | 接话现场合成 | 只备「明白。」「好的。」 | 八句固定接话全备 |
| --- | ---: | ---: | ---: |
| 候选人说完到听到接话 | 2.2 到 3.4 秒 | 1.1 到 1.6 秒 | 1.0 到 1.4 秒 |
| 接话播完到问句开始 | | 1.2 到 2.7 秒 | 0 到 0.8 秒 |

最后一列是按真实面试的节奏量的（候选人等面试官说完才回答，`AI_INTERVIEW_LIVE_REAL_PACE=1`），开口的 11 轮接话全部是现成的，现场的问句一条都没有排队。

接话越短，播完以后空得越久，所以引擎把接话换成了两秒左右的固定句子（#163）。把现场合成的声学生成步数从 25 调到 16（`AI_INTERVIEW_TTS_LIVE_DIFFUSION_STEPS`，语音线的开关，默认不调），最后一行是 0 到 0.3 秒。要连这点空白也去掉只能边合成边播（三个引擎里只有 BreezeTTS2 做得到，见 #13）。

备这八句在真引擎上要 13 到 16 秒，一句一句排着做。合成服务一次只做一句，所以它给现场的句子让路：每句开工前先看这个进程里有没有面试官正在现场接话（从开始想到这一轮的话都备好），有就等它接完，最多等一分钟。不让的话，两边撞上时问句会排在它后面多等 0.7 到 2.3 秒（没有让路、候选人又抢着回答的那一场量到的）。已经在做的那一句不打断，现场的第一句最多被它挡两秒。正常的面试里两边撞不上：实测第一轮要接话是在面试开始 45 秒以后，那时八句早备完了，`waited_ms` 是 0。没赶上的那一句现场合成，和没备一样。`crates/interview-server/tests/live.rs` 默认不等开场白播完就让候选人答完，那样跑会看到两边抢；要看真实的节奏，加 `AI_INTERVIEW_LIVE_REAL_PACE=1`。

后端日志里「实时对话接了一轮」的 `synth_ms` 是这一轮现场合成一共用了多久，`first_ready_ms` 是多久之后第一句可以播；「接话提前合成好了」那一行是开始时备这几句用了多久（`total_ms`），其中多少是在给现场的句子让路（`waited_ms`）。

想自己量：`web/apps/candidate` 里 `E2E_REAL=1 AI_INTERVIEW_LOG=info … pnpm e2e -g 实时对话`（见那边的 README），测试会打印每一轮的时间线和中位数、p95，后端日志里「实时对话接了一轮」那几行是服务端各段用了多久。

## 面试链接

- 链接是 `{PUBLIC_URL}/i/#<令牌>`。令牌在 `#` 后面，浏览器不会把它发给服务器，也就进不了访问日志和 Referer。页面取出令牌后放在请求头 `Authorization: Bearer <令牌>` 里。
- 令牌是 256 位随机数。库里只存 SHA-256（`interview_invites.token_hash`），完整链接只在生成时返回一次。
- 令牌不进日志：`tests/invites.rs` 里有一条测试把所有级别的日志（包括数据库的查询日志）收下来检查。长得不像令牌的（不是 43 个 URL 安全 base64 字符）直接拒绝，不查库。
- 没有对校验失败做限速。令牌有 256 位，猜不出来，限速防不了什么；而服务进程拿不到可信的客户端地址，按地址限速做在这里容易误伤同一个出口的候选人。要挡刷接口的流量，放在反向代理上。
- 默认 7 天过期（`AI_INTERVIEW_INVITE_TTL_HOURS`），生成时可以指定，最长 30 天。
- 重新生成会让旧链接作废，保证同一时间只有一条能用；请求里带 `keep_existing` 可以保留旧的。
- 有效期只管「能不能开始」：面试已经开始的不会因为到期被赶出去；结束后 24 小时内链接还能用来补传没传完的录像。
- 候选人侧的 handler 参数里写一个 `RoomAccess`，令牌校验就做完了，里面有面试的 ID 和当前状态。

## 现场转写

代码在 `src/transcribe.rs`，服务进程里由 `Deps::with_stt` 接上（测试可以用 `Deps::with_transcriber` 换成假的）。

- 候选人的声音只有录像这一条上行的路。每一段正在上传的录制对应一个 `interview_stt::RecordingTranscript`：分片存好后马上喂给它（常驻的 ffmpeg 解出声音，边到边识别），所以一题答完时文字基本已经有了。
- 判断回答时按这段回答的起止时刻取文字：从面试官那句话播完算起，到候选人答完为止。面试官的声音就算被麦克风收进去，也不会算成候选人说的。回答结束时最后一小段录像可能还在路上，最多等 5 秒（页面会在答完时立刻把手头的录像传上来），等不到就用已经到了的部分。
- 文字、逐字时间、置信度和识别后端一起写进 `interview_turns`。日志里只有面试和录制的 ID，没有文字。
- 这些都只在内存里。服务重启、解码出错之后，下一次要文字时用存下来的分片重建，已经答完的部分只解码、不重新识别。分片合并后就删了，那之后重建不了，这一段就不判断。面试结束时释放；一场面试最多同时留 4 段。
- 单独的音频轨（没有摄像头时）和摄像头轨都有的话用音频轨。屏幕轨不转写。
- 拿不到文字的几种情况都不影响面试，只是不追问：没装 ffmpeg（启动后第一次用到时提醒一次）、语音识别没配或者用不了、录像解不开。
- 假的识别后端（`AI_INTERVIEW_STT_BACKEND=fake`，默认）给的是固定的文字，不是候选人说的话，默认不做现场转写。联调和端到端测试想看整条链路通不通时设 `AI_INTERVIEW_ROOM_FAKE_TRANSCRIPT=true`。

## 录制

- 页面边录边传，一片一个请求；分片存在 `interviews/{面试}/recordings/{轨道}/{第几段}/chunks/{序号}`。
- 同一个分片传几次结果都一样，留第一次的。重试和上一次请求同时到的时候，后到的等前一个写完（按段和序号加数据库的咨询锁），所以登记的大小、校验和和存下来的内容一定是同一次请求的。第二次传来的内容和第一次不一样时（页面那边出了问题才会这样）照样返回成功，因为页面拿到别的回答也补救不了，但会在日志里留一条警告，带着面试、录制段的 ID 和序号。
- 一段传完后排一个后台任务 `recording.assemble`：按序号把分片接成 `recording.webm`（或 `.mp4`），用 ffmpeg 原样重新封装补上时长，读出时长写进 `interview_recordings.duration_ms`，然后删掉分片。
- ffmpeg 是可选的（`AI_INTERVIEW_FFMPEG`、`AI_INTERVIEW_FFPROBE`，默认从 PATH 里找）。没装时录像照样能从头播放，只是拖不了进度条，`error` 里会写一句说明。
- 合并失败会重试，三次都不行就标成 `failed`，分片留在磁盘上。
- 一段录制的身份是浏览器生成的 UUID（`client_segment_id`），所以登记、上传、完成都可以放心重试。
- 协议的细节在 `docs/architecture/api.md` 的「录制上传」。

## 同意事项

内容在 `src/consent.rs`。改了任何一项的文字都要换一个新的 `CONSENT_VERSION`：库里按版本记候选人同意的是哪一版（连同当时的标题），版本变了要重新确认。

## 展示信息

没设置时页面显示「AI 面试」。

## 隐私

- 日志只记面试和链接的 ID，不记令牌、候选人的姓名和回答。回答的文字只进数据库。
- 会话信息里只有岗位名称和候选人的称呼，不带手机、邮箱和简历。
- 过程事件只记发生了什么，不带内容（粘贴只有字符数，设备变化只有类别和个数）。

DATABASE_URL=$(scripts/dev-db.sh url) cargo test -p interview-room

## 本地联调

`examples/demo.rs` 造一场准备好的面试（合成的岗位、候选人和题目，面试官的语音是提示音），不用先走出题和语音合成就能把面试间从头到尾跑一遍。它直接写库，只对着自己机器的开发库用，环境变量要和服务进程一样：

```bash
export DATABASE_URL=$(scripts/dev-db.sh url)
cargo run -p interview-room --example demo -- seed            # 打印面试的 ID 和链接
cargo run -p interview-room --example demo -- state <面试的 ID>   # 状态、对话记录、过程事件、录像
```

`seed` 可以带 `--silence-sec`、`--min-sec`、`--max-sec`（答题的时间设置）、`--tone-ms`（提示音多长）和 `--realtime 1`（配成实时对话）。候选人页面的浏览器端到端测试（`web/apps/candidate/e2e`）就是用它造数据、查结果的。

新加了迁移文件之后如果测试报 500 或者说列不存在，是 `interview-platform` 里嵌进去的迁移没有重新编译，`touch crates/interview-platform/src/db.rs` 再跑。
