# 实时对话模式：方案和实测

逐题模式是「念一道题，听完，再念下一道」。实时对话模式下，面试官听完候选人的话会现场接话：追问、回应候选人的问题，或者进入下一题。代码在 `src/live.rs`，用真模型跑一场的命令见本目录上一级的 `README.md`。

这份文档写三件事：引擎是怎么做的，用 deepseek-flash 实测的延迟和费用，整条链路（加上语音识别和语音合成）的延迟预算和还没解决的问题。

## 做法

### 题目还是提前出好的

实时模式不是让模型自由发挥一整场。出题器照样提前出一份 `InterviewPlan`，它在这里是提纲：

- 开场白、每道主问题、过渡语、结束语都提前合成好语音。
- 只有追问和回应是现场生成、现场合成的。

这样做有三个好处。考察范围、必问题、时间分配仍然由 HR 的配置和出题器决定，不会跑偏。实测大约一半的轮次是「进入下一题」，这些轮次不需要现场合成，模型一做出决定就能播。模型出错或者超时的时候，面试退回到按顺序问题目，不会卡住。

### 每轮只调一次模型，第一行就是决定

候选人说完一段，引擎调一次模型，流式读输出。第一行是两个词：动作和对这道题到目前为止的判断。

```text
probe weak
明白。那个方案里你本人负责哪一块？
```

```text
next adequate
讲了订单系统的拆分，主要是参与者。
数字说不出来源
```

动作有四种：

| 动作 | 含义 | 之后的输出 |
| --- | --- | --- |
| `probe` | 就当前这道题追问一句 | 要念的话，按句子流式给出 |
| `reply` | 候选人在反问、要求重复、要求解释题目，简短回应后带回当前这道题 | 要念的话 |
| `next` | 这道题问够了，往下走 | 这道题的一句话概括，加上值得 HR 留意的情况，不念 |
| `end` | 候选人明确不想继续 | 同上 |

第一行一到，动作就定了。是 `next` 的话，过渡语和下一题（都是提前合成的）马上可以播，不用等模型把概括写完。是 `probe` 的话，后面每出来一句就交给语音合成。

没有用 JSON 输出，也没有用工具调用：JSON 要等整个对象闭合才能解析，工具调用的参数同样要等完整。「第一行是决定，后面是正文」是能边收边用的最简单的格式。模型偶尔不按格式写时，引擎把整行当成要说的话处理。

### 上下文：固定的部分放前面，问完的题只留一行

每轮发给模型两条消息：

1. **系统消息**，整场面试不变：规则、这场面试的背景（轮次、语言、风格、公司介绍、岗位和候选人的摘要、要核实的点）、提纲（每道题的题面、想看什么、好的回答里应该有什么、需要警惕什么、追问方向）。
2. **用户消息**，每轮重新拼：已经问完的题每道一行（判断加一句话概括）；当前这道题到现在的对话，逐字；状态（面试进行了多久、计划多久、后面还有几道必须问的题、这道题还能不能追问）。

换题时，当前这道题的逐字对话被压成一行概括，概括就是模型在 `next` 那一轮顺手写的，不需要单独调一次模型做压缩。所以不管面试多长，每轮的输入大小基本不变：实测每轮 3300 到 3600 个输入 token，其中 88% 左右命中缓存（系统消息完全相同，DeepSeek 的缓存按前缀匹配）。

概括和「值得 HR 留意的情况」同时写进这道题的 `AnswerNote`，报告那边可以直接用。

### 哪些事由代码管，不交给模型

模型只负责「听懂了没有、该怎么接」。下面这些是代码管的：

- **能不能追问**：每道题最多追问 `follow_ups.max_per_question × 2` 次；再问一轮会让必须问的题问不完时也不让问。不能追问时提示词里会写明，模型还是选了 `probe` 的话，引擎改成 `next`。
- **念到哪为止**：追问和回应只念到第一个问句为止，最多四句、160 个字，后面的内容丢掉。测试时遇到过模型在追问后面接着写这道题的概括，这样的内容不能念给候选人听。
- **回应次数**：一道题上最多回应候选人 3 次，免得被带着闲聊。
- **换题之后问什么**：下一题、时间不够时跳过可选题、时间有富余时问备用题、请候选人提问、结束语，全部走逐题模式的同一个状态机（`session::step`）。
- **提前结束**：最近几道题都答不上来就结束，规则和逐题模式相同，用的是模型在第一行给的判断。
- **没开口**：不调模型。提醒一次并重问，还是没有就下一题，连续两题没声音就结束。
- **模型出错或 20 秒没反应**：按顺序进入下一题。已经说出口的半句话照样算数。

### 给调用方的接口

```rust
let (state, first) = live::open(&plan, &config)?;            // 开场白加第一题
let outcome = live::respond(&model, &plan, &config, &state, &turn, &mut sink).await?;
```

- `turn` 是候选人刚说完的一段：转写文字、面试进行到的时间、这段话的时长。
- `sink` 陆续收到 `LiveEvent`：`Action`（定了怎么接）、`Speak { key, text }`（现场生成的一句，马上送去合成；同一轮的几句 `key` 相同，例如 `q3.p1`、`q3.r1`）、`Play { utterance }`（播一句提前合成好的）。
- 返回的 `outcome` 里有新的状态（存回 `interviews.runtime_state`）、这一轮说过的话（现场生成的那句已经拼成完整的一句，可以记进 `interview_turns`）、接下来怎么听（`listen`）或者为什么结束（`finished`）、进度、用量、各个时间点。

对应到 `docs/architecture/api.md` 里的 WebSocket 消息：`Action` 之前发 `thinking`；`Speak` 对应 `speak_begin`（`mode` 为 `stream`）加音频帧；`Play` 对应 `speak_begin`（`mode` 为 `url`）；一轮结束后发 `listening` 或 `finished`。

## 实测

2026-11-13，deepseek-flash，思考关闭，候选人由另一个模型按人设扮演。延迟从拿到候选人的转写文字开始算，含网络往返（云端容器到 DeepSeek）。几场之间提示词有过小的调整，不影响延迟。

| 场次 | 轮数 | 追问 / 回应 / 下一题 | 定下动作（中位 / 90%） | 追问的第一句（中位 / 90%） | 费用（空闲 / 高峰） |
| --- | --- | --- | --- | --- | --- |
| 后端 20 分钟，回答空泛 | 28 | 16 / 1 / 11 | 1.10 秒 / 1.33 秒 | 1.20 秒 / 1.39 秒 | 0.017 元 / 0.034 元 |
| 后端 20 分钟，真做过 | 16 | 7 / 0 / 9 | 1.29 秒 / 1.71 秒 | 1.32 秒 / 1.73 秒 | 0.014 元 / 0.028 元 |
| 后端 20 分钟，简历注水 | 22 | 10 / 1 / 11 | 1.02 秒 / 1.28 秒 | 1.07 秒 / 1.38 秒 | 0.011 元 / 0.023 元 |
| 后端 20 分钟，爱反问 | 21 | 8 / 2 / 11 | 1.06 秒 / 1.28 秒 | 1.13 秒 / 1.61 秒 | 0.012 元 / 0.025 元 |
| 客户成功 30 分钟，回答空泛 | 40 | 23 / 1 / 16 | 1.05 秒 / 1.23 秒 | 1.18 秒 / 1.40 秒 | 0.023 元 / 0.046 元 |
| 客户成功 30 分钟，爱反问 | 32 | 12 / 4 / 16 | 1.01 秒 / 1.18 秒 | 1.12 秒 / 1.20 秒 | 0.021 元 / 0.042 元 |
| 后端 20 分钟，完全不会 | 6 | 3 / 0 / 3 | 1.14 秒 / 1.27 秒 | 1.20 秒 / 1.30 秒 | 0.005 元 / 0.011 元 |
| 后端 20 分钟，中途不想面了 | 3 | 1 / 0 / 1（另有 1 次结束） | 0.92 秒 / 1.17 秒 | 1.33 秒 | 0.004 元 / 0.009 元 |

结论：

- **定下动作大约 1 秒**。多数场次里 90% 的轮次在 1.4 秒以内，最慢的一场是 1.7 秒。追问的第一句话比决定晚 0.1 到 0.2 秒。
- **一场面试的模型费用两三分钱**，比出题（约 0.1 元）还便宜。
- **打开思考（low）**：同一场面试，定下动作中位 1.48 秒、90% 在 2.14 秒以内，费用多一半左右，追问的质量没有看出明显差别。实时模式建议保持思考关闭（`live_thinking` 的默认值）。
- 「完全不会」的候选人问了三道题后提前结束；「不想面了」的候选人说完那句话的当轮就结束；「回答空泛」的候选人被追问到说出「核心代码是同事写的」为止，记录里留下了「简历把该方案作为个人核心成果，与自述不符」。

对话质量上看到的问题和处理：

- 模型接话时爱带一句评价（「讲得挺清楚」）。提示词里明确禁止并给了反例之后基本消失，偶尔还有。
- 早期版本一段话里会连问两个问题、提前问提纲里后面的题。提示词改成「只问一句」「只追问当前这道题」之后没有再出现。
- 追问的长度现在是 20 到 35 个字，加上一句很短的接话。这个长度是为语音合成的速度定的，见下一节。

## 整条链路的延迟预算

候选人最后一个字说完，到听见面试官的声音，中间有四段：

| 环节 | 现在的数字 | 来源 |
| --- | --- | --- |
| 判断候选人说完了 | 实时模式下的数字待测。逐题模式用的是 3 到 10 秒的静音，实时模式不能用这个，要靠语义判断（Smart Turn）加 1 秒左右的静音 | 语音线 |
| 转写收尾 | 边录边转时，每句话说完约 0.8 秒文字定下来，其中 0.6 秒是在等停顿，和「判断说完了」是重叠的 | 语音线实测，见 `docs/speech/stt.md` |
| 模型定下动作 | 约 1 秒，慢的时候 1.7 秒 | 本文实测 |
| 语音合成 | 下一题：0，音频是提前合成的。追问：取决于第一句有多长，见下面 | 语音线 |

**进入下一题**（约一半的轮次）：判断说完和转写收尾是同时进行的，再加模型的 1 秒。如果判断说完能做到 1.5 秒，候选人说完 2.5 秒左右听到「好的，谢谢」加下一题。这和真人面试官的节奏差不多。

**追问**：语音线在 M3 Max 上测到的合成速度是实际语速的 1.25 到 1.5 倍（实时率 0.67 到 0.80）。也就是说，一句 5 秒的话要合成 3.5 到 4 秒才能开始播。所以：

- 模型先说的那句很短的接话（「明白。」）合成很快，候选人说完大约 3 秒能听到。
- 真正的问句有 20 到 35 个字，整句合成要 3 到 5 秒。接话播完之后会有两三秒的空白。

这段空白是实时模式目前最大的体验问题，引擎这边已经把能做的做了（先出短接话、问句尽量短、一出句子就送合成）。剩下的要语音线来解决，有三个方向：

1. **按逗号切开合成**。问句的前半句（10 个字左右）先合成先播，播的时候合成后半句。合成比播放快，所以只要第一段出来了，后面不会断。代价是每段单独合成，语调可能不连贯，需要实际听。引擎给出的是整句，切分可以在合成那一层做。
2. **候选人一说完就播一个提前合成的语气词**（「嗯。」），盖住模型的 1 秒。逐题模式已经这么做了（`listen.ack`）。实时模式要注意不能用「好的，谢谢」这种听起来像要换题的话。
3. **实时模式换用三个引擎里最快的那个**，音色和逐题模式保持一致的前提下。

候选人打断面试官（面试官还在说，候选人开口了）目前没有专门处理：引擎把面试官那句话当作完整说完了。需要的话可以在调用 `respond` 时告诉引擎上一句实际播到哪里，等语音线的打断检测有了再加。

## 和逐题模式怎么选

| | 逐题模式 | 实时对话模式 |
| --- | --- | --- |
| 追问 | 提前写好的，每题默认最多 1 个 | 现场生成，贴着候选人刚说的话问 |
| 候选人反问、要求重复 | 只能重念题目 | 能回应 |
| 模型多久做出决定 | 1.1 到 1.3 秒，有过渡语盖住 | 1.0 秒 |
| 需要现场合成语音 | 不需要 | 追问和回应需要 |
| 需要流式语音识别 | 不需要（可以面试后整段转写） | 需要 |
| 一场的模型费用 | 不到 0.02 元 | 0.01 到 0.05 元 |
| 现在能不能用 | 能 | 引擎能用；整条链路要等流式识别、判断说完、现场合成接上 |

配置里的 `mode` 选 `conversational` 就是实时对话模式。两种模式用同一份出题结果，出题时不用区分。
