# 实时对话模式：方案和实测

逐题模式是「念一道题，听完，再念下一道」。实时对话模式下，面试官听完候选人的话会现场接话：追问、回应候选人的问题，或者进入下一题。代码在 `src/live.rs`，用真模型跑一场的命令见本目录上一级的 `README.md`。

这份文档写三件事：引擎是怎么做的，用 deepseek-flash 实测的延迟和费用，整条链路（加上语音识别和语音合成）的延迟预算和还没解决的问题。语音那一侧的分段实测在 `docs/speech/realtime.md`。

## 做法

### 题目还是提前出好的

实时模式不是让模型自由发挥一整场。出题器照样提前出一份 `InterviewPlan`，它在这里是提纲：

- 开场白、每道主问题、过渡语、结束语都提前合成好语音。
- 只有追问和回应是现场生成、现场合成的。

这样做有三个好处。考察范围、必问题、时间分配仍然由 HR 的配置和出题器决定，不会跑偏。实测大约一半的轮次是「进入下一题」，这些轮次不需要现场合成，模型一做出决定就能播。模型出错或者超时的时候，面试退回到按顺序问题目，不会卡住。

### 每轮只调一次模型，第一行就是决定

候选人说完一段（或者刚停下来，见下面「候选人停了一下」），引擎调一次模型，流式读输出。第一行是两个词：动作和对这道题到目前为止的判断。

```text
probe weak
明白。那个方案里你本人负责哪一块？
```

```text
next adequate
讲了订单系统的拆分，主要是参与者。
数字说不出来源
```

动作有六种：

| 动作 | 含义 | 之后的输出 |
| --- | --- | --- |
| `probe` | 就当前这道题追问一句 | 要念的话，按句子流式给出 |
| `reply` | 候选人在反问、要求解释题目、没听清上一句追问，简短回应后带回当前这道题 | 要念的话 |
| `next` | 这道题问够了，往下走 | 这道题的一句话概括，加上值得 HR 留意的情况，不念 |
| `end` | 候选人明确不想继续。模型选了以后引擎还要再核对一次，见下面「结束面试之前再核对一次」 | 同上 |
| `repeat` | 把当前这道题的题目原样再念一遍。候选人没听清题目，或者题目被打断没听全 | 没有。「好的，我再说一遍」和题目都是提前合成的 |
| `wait` | 候选人的话还没说完，接着听。只在候选人刚停下来时可以选 | 没有。这一轮什么都不说，状态不变 |

第一行一到，动作就定了（`end` 除外，要等核对完）。是 `next` 的话，过渡语和下一题（都是提前合成的）马上可以播，不用等模型把概括写完。是 `probe` 的话，后面每出来一句就交给语音合成。

没有用 JSON 输出，也没有用工具调用：JSON 要等整个对象闭合才能解析，工具调用的参数同样要等完整。「第一行是决定，后面是正文」是能边收边用的最简单的格式。模型偶尔不按格式写时，引擎把整行当成要说的话处理。

### 上下文：固定的部分放前面，问完的题只留一行

每轮发给模型两条消息：

1. **系统消息**，整场面试不变：规则、这场面试的背景（轮次、语言、风格、公司介绍、岗位和候选人的摘要、要核实的点）、提纲（每道题的题面、想看什么、好的回答里应该有什么、需要警惕什么、追问方向）。
2. **用户消息**，每轮重新拼：已经问完的题每道一行（判断加一句话概括）；当前这道题到现在的对话，逐字；状态（面试进行了多久、计划多久、后面还有几道必须问的题、这道题还能不能追问）。

换题时，当前这道题的逐字对话被压成一行概括，概括就是模型在 `next` 那一轮顺手写的，不需要单独调一次模型做压缩。所以不管面试多长，每轮的输入大小基本不变：实测每轮 3300 到 3600 个输入 token，其中 88% 左右命中缓存（系统消息完全相同，DeepSeek 的缓存按前缀匹配）。

概括和「值得 HR 留意的情况」同时写进这道题的 `AnswerNote`，报告那边可以直接用。

### 哪些事由代码管，不交给模型

模型只负责「听懂了没有、该怎么接」。下面这些是代码管的：

- **能不能追问**：每道题最多追问 `follow_ups.max_per_question × 2` 次；再问一轮会让必须问的题问不完时也不让问。不能追问时提示词里会写明，模型还是选了 `probe` 的话，引擎改成 `next`。
- **念到哪为止**：追问和回应只念到第一个问句为止，最多四句、160 个字，后面的内容丢掉。测试时遇到过模型在追问后面接着写这道题的概括，这样的内容不能念给候选人听。
- **回应次数**：一道题上最多回应候选人 2 次，追问和回应加起来不超过追问上限加 1 次（默认配置下是 3 次），免得被带着闲聊，或者围着一道题来回绕。到了上限提示词里会写明，模型还是选了 `reply` 的话，引擎改成 `next`。面试最后请候选人提问的环节最多回应 3 次。
- **结束面试**：模型选了 `end`，引擎要再问一次模型核对，核对通过才结束，见下面「结束面试之前再核对一次」。
- **换题之后问什么**：下一题、时间不够时跳过可选题、时间有富余时问备用题、请候选人提问、结束语，全部走逐题模式的同一个状态机（`session::step`）。
- **提前结束**：最近几道题都答不上来就结束，规则和逐题模式相同，用的是模型在第一行给的判断。
- **没开口**：不调模型。提醒一次并重问，还是没有就下一题，连续两题没声音就结束。
- **重念题目**：同一道题只重念一次。重念过了提示词里会写明，模型还是选了 `repeat` 的话，引擎改成 `next`。
- **接着听**：只有候选人刚停下来（`paused`）时才算数。这一轮已经结束了模型还选 `wait`，引擎改成 `next`。
- **被打断时候选人听到了哪**：按播放进度算，不交给模型猜，见下面「候选人打断面试官」。
- **模型出错或 20 秒没反应**：按顺序进入下一题。已经说出口的半句话照样算数。候选人只是停了一下的时候出错，算作 `wait`，等这一轮真的结束再问一次。

### 结束面试之前再核对一次

「候选人要求结束」会写进面试记录和报告，HR 看到的是「候选人中途不想面了」。判错的代价比别的动作大，所以不只听一次模型的。

实际跑的时候遇到过这种情况：候选人的声音和题目完全无关（测试用的是一段不相干的录音），模型在一道题上重念、回应、追问来回绕了五六轮，最后选了 `end`。面试记成了「候选人要求结束」，可候选人一个字都没提过不想面。

现在分两层处理：

- **答非所问怎么接**写进了提示词：第一次用一句话把候选人带回当前这道题（`reply`）；带回过一次还是无关，就选 `next`，判断写 `no_answer`，不再问第三遍，也不选 `end`。连着几道题这样，引擎按「最近几道题都答不上来」提前结束，结束原因是 `poor_answers`。
- **模型选了 `end`，引擎再问一次模型**：只把面试官的上一句话和候选人这一轮说的话发过去，只问一件事，候选人有没有明确表示不想继续，回答 `yes` 或 `no`。答非所问、答得差、想跳过这道题都不算。回答 `yes` 才结束，结束原因是 `candidate_request`。回答 `no`、出错或者 8 秒没反应，这一轮改成 `next`（模型原来的判断是 `no_answer` 就保留，否则记成 `poor`），面试接着往下走。

这一步用的是模型而不是关键词：候选人不想面了的说法太多（「我觉得不太合适」「要不今天就到这吧」「我这边有点事」），列不全，也容易把「这道题我不想答」误当成不想面。

代价是结束那一轮的 `Action` 要多等一次模型调用，实测一共 2.0 秒左右（平时 1 秒）。一场面试最多发生一次，结束语是提前合成的，候选人感觉到的是面试官停了两秒才说再见。别的动作不受影响。

### 给调用方的接口

```rust
let (state, first) = live::open(&plan, &config)?;            // 开场白加第一题
let outcome = live::respond(&model, &plan, &config, &state, &turn, &mut sink).await?;
```

- `turn` 是候选人这一轮到现在说的话：转写文字、面试进行到的时间、这段话的时长。
- 候选人只是停了一下，或者是打断面试官开的口，改用 `live::respond_with`，多传一个 `TurnContext`（`paused` 和 `interrupted`），下面两节讲。`respond` 就是两样都不填的 `respond_with`。
- `sink` 陆续收到 `LiveEvent`：`Action`（定了怎么接）、`Speak { key, text }`（现场生成的一句，马上送去合成；同一轮的几句 `key` 相同，例如 `q3.p1`、`q3.r1`）、`Play { utterance }`（播一句提前合成好的）、`Done { listen, finished, progress }`（这一轮要说的话都给出来了）。
- `Done` 每一轮只发一次，在它之后不会再有 `Speak` 和 `Play`。它带的 `listen`、`finished`、`progress` 和最后返回的 `outcome` 里的一样，发出以后不会再变，模型后面出错或超时也一样。调用方拿到它就知道这一轮说完之后是接着听候选人还是面试结束，可以把手里最后一句话放出去，不用等 `respond` 返回。换题时模型在 `Done` 之后还要写这道题的概括，早多少见下面的实测。
- 返回的 `outcome` 里有新的状态（存回 `interviews.runtime_state`）、这一轮说过的话（现场生成的那句已经拼成完整的一句，可以记进 `interview_turns`）、接下来怎么听（`listen`）或者为什么结束（`finished`）、进度、用量、各个时间点。

对应到 `docs/architecture/api.md` 里的 WebSocket 消息：`Action` 之前发 `thinking`；`Speak` 对应 `speak_begin`（`mode` 为 `stream`）加音频帧；`Play` 对应 `speak_begin`（`mode` 为 `url`）；收到 `Done` 就可以定下这一轮的话播完后发 `listening` 还是 `finished`。

### 候选人停了一下：说完了没有

候选人停顿半秒多，语音线的 `TurnListener` 会发 `JudgeWanted`，请调用方判断这段话是不是说完了。这个判断并在 `respond` 里，不用另外调一次模型：

```rust
// 收到 TurnEvent::JudgeWanted { revision, text }
let turn = CandidateTurn { text, elapsed_ms, answer_ms };
let context = TurnContext { paused: true, interrupted };
let outcome = live::respond_with(&model, &plan, &config, &state, &turn, &context, &mut sink).await?;
```

- 模型认为没说完：第一行是 `wait`。`sink` 收到 `Action { action: Wait }`，这时调 `turn.verdict(revision, false)`。`outcome.state` 和传进来的一样，什么都不用存。
- 模型认为说完了：第一行是别的动作，和平时一样。`sink` 一收到 `Action` 就可以调 `turn.verdict(revision, true)`，这一轮会提前结束。`Speak` 的句子可以先送去合成，`Play` 的音频本来就是现成的。
- 这次的结果要等 `TurnEvent::Ended` 才能用：`Ended` 里的文字和这次问的一样，就把 `outcome.state` 存下来、把音频发出去；候选人接着说了（又来了 `SpeechStarted`），整个丢掉，等下一次 `JudgeWanted` 或者 `Ended` 再问。丢掉的那次调用不到一厘钱。
- `Ended` 来的时候手里没有可用的结果（比如上一次是 `wait`，候选人之后一直没出声），用 `paused: false` 再调一次。这时模型不能再选 `wait`。
- 还没认出字（`text` 是空的）时带着 `paused: true` 来问，引擎不调模型，直接返回 `wait`。

模型怎么判断：停在半句话上，停在「然后」「就是」「比如说」「因为」这类词上，说了「主要有三点」只讲了两点，只开了个头，都是没说完。意思完整的话算说完了，哪怕很短、很空泛，「不知道」「就这些」也算。标点是语音识别加的，不作数。

### 候选人打断面试官

面试官还在说，候选人开口了。语音线的 `BargeInDetector` 发现以后，面试间停掉播放，把断在哪里告诉引擎：

```rust
let context = TurnContext {
    paused,
    interrupted: Some(Interruption {
        utterance_key: "q3".into(),   // 被打断时正在播的那一句：Speak 或 Play 里的 key
        played_ms: 2600,              // 这一句从开始播到被打断过了多久
        total_ms: Some(9800),         // 这一句完整播完要多久；现场合成的还不知道就留空
    }),
};
```

- `played_ms` 用浏览器 `playback` 消息里这一句开始播的时刻，和 `BargeInDetector::detected_at_ms()` 相减。现场生成的追问分成几句送去合成，它们的 `key` 相同，从第一句开始播算起。
- 引擎按比例算出候选人听到了哪几个字；不知道总长时按语速估（中文一个字 0.22 秒）。断在前面的过渡语或开场白上，后面的题目就算一个字都没听到。上一轮面试官说了哪几句记在状态里（`last_said`），`utterance_key` 对不上的话当作没被打断。
- 同一轮里每次调 `respond_with`（停顿时问的、结束时问的）都要带上 `interrupted`。`wait` 不改状态，引擎不会替调用方记着。
- 面试官已经说完了候选人才开口，不算打断，不用带。

模型看到的对话里，被打断的那句话分成两截：

```text
面试官：你简历里写库存扣减用的是 Redis 预扣【说到这里被候选人打断，没说出来的部分：加消息队列异步落库。我想具体听一下，你们是怎么保证不超卖的？】
候选人：不好意思，刚才没听清。
```

模型据此决定怎么接：候选人听到的够他明白问的是什么、并且在回答，就照常追问或下一题；题目没听全、候选人说的是别的事（还在补充上一道题、问能不能听到），选 `repeat`；被打断的是追问或回应，用 `reply` 把它更短地再说一遍。

对话记录里（`interview_turns`）面试官那句话记的还是完整的文字。要记实际说出口的部分，用状态里对话的最后一句面试官的话（`unheard` 是没说出来的后半句）。

结论：

- **定下动作大约 1 秒**。多数场次里 90% 的轮次在 1.4 秒以内，最慢的一场是 1.7 秒。追问的第一句话比决定晚 0.1 到 0.2 秒。
- **一场面试的模型费用两三分钱**，比出题（约 0.1 元）还便宜。
- **打开思考（low）**：同一场面试，定下动作中位 1.48 秒、90% 在 2.14 秒以内，费用多一半左右，追问的质量没有看出明显差别。实时模式建议保持思考关闭（`live_thinking` 的默认值）。
- **`Done` 比函数返回早多少**（两场，后端 20 分钟，回答空泛和爱反问）：换题的 15 轮里，`Done` 和第一句要播的话同时出来，比等模型写完这道题的概括早 0.3 到 0.4 秒（中位），最多 0.7 秒。追问和回应的 18 轮没有差别：问句一出来模型就停笔了，`Done` 和函数返回几乎同时。所以它省下的是换题那一轮的等待。
- 「完全不会」的候选人问了三道题后提前结束；「不想面了」的候选人说完那句话的当轮就结束，结束原因是 `candidate_request`；「答非所问」的候选人（一直在说和面试无关的话，从不提不想面）每道题被带回一次、再无关就下一题，三道题后提前结束，结束原因是 `poor_answers`，改之前同一个人设要 15 轮，一道题上绕五六轮；「回答空泛」的候选人被追问到说出「核心代码是同事写的」为止，记录里留下了「简历把该方案作为个人核心成果，与自述不符」。

对话质量上看到的问题和处理：

- 模型接话时爱带一句评价（「讲得挺清楚」）。提示词里明确禁止并给了反例之后基本消失，偶尔还有。
- 早期版本一段话里会连问两个问题、提前问提纲里后面的题。提示词改成「只问一句」「只追问当前这道题」之后没有再出现。
- 追问的长度现在是 20 到 35 个字，加上一句很短的接话。这个长度是为语音合成的速度定的，见下一节。

### 停顿和打断判断得准不准

2026-11-13，deepseek-flash，思考关闭。`examples/turn_taking.rs` 里 31 个有标准答案的例子，每个跑 3 遍，一共 93 次。下面是最后一遍的结果：

| 情况 | 例子 | 判对 |
| --- | --- | --- |
| 候选人没说完，应该接着听 | 12 个：句子说到一半（包括识别给加了句号的）、停在「然后」「比如说」「因为」上、只开了个头、说三点只讲到第二点 | 36 次里 36 次 |
| 候选人说完了，不应该再等 | 12 个：完整的回答、只答了两句、「不太清楚」、很空泛的话、「大概就是这样」、反问、没听清题目、追问到上限以后没听清追问、不想面了、第一次答非所问、带回过一次还是答非所问 | 36 次里 36 次，并且接的动作也对（没听清题目就重念，没听清追问就换个说法再说一遍，不想面就结束，第一次答非所问带回来，再无关就下一题） |
| 面试官被打断 | 7 个：题目播到三成候选人说没听清、开场白没播完候选人问能不能听到、题目播到三成候选人请面试官说慢一点、题目快播完候选人直接回答、刚说过渡语候选人还在补充上一题、追问说到一半没听清、追问快说完候选人抢答 | 21 次里 21 次 |

- 加答非所问这两个例子之前，同样的提示词有一遍是 87 次里对了 86 次。错的那一次是「第二句说到一半，识别给加了句号」：截出来的那半句碰巧读着像一句完整的话，模型当成说完了。这种情况光看文字分不出来，要靠语音线再等到 3.1 秒没有声音才结束这一轮来兜底。
- 定下「接着听」中位 1.06 秒；定下别的动作中位 1.02 秒，要说的第一句中位 1.10 秒。几遍之间中位数在 0.95 到 1.18 秒之间浮动，和平时接话一样，并进来以后没有变慢。
- 93 次一共 0.030 元（空闲时段），一次不到一厘钱。
- 例子里候选人的话是写出来的文字，不是真人录音转写的。真人说话的停顿、口头禅、识别错字更多，上线前要用真实的面试录音再看。
- 调提示词时遇到过两种错。一种是追问被打断、候选人说没听清，模型选了 `repeat`，重念的是题目而不是追问。另一种是这道题已经追问到上限，候选人说没听清追问，模型又写了一句追问，被引擎改成下一题，等于没理候选人。现在没听清追问一律走 `reply`，状态里会写明「你上一句说的是追问，不要选 repeat，选 reply 把原来的意思更短地再说一遍」。

## 整条链路的延迟预算

候选人最后一个字说完，到听见面试官的声音，中间有四段。语音线在 2026-11-13 把前后两段都测了，完整的数字和测法见 `docs/speech/realtime.md`，这里只列和引擎有关的。

| 环节 | 实测 | 来源 |
| --- | --- | --- |
| 发现候选人停下来了，这段话的文字定稿 | 0.84 秒，其中 0.6 秒是在等停顿 | 语音线 |
| 模型定下动作（包括「说完了没有」） | 约 1 秒，慢的时候 1.3 秒 | 本文 |
| 追问的第一句写出来 | 比定下动作晚 0.05 到 0.2 秒 | 本文 |
| 语音合成出第一块音频 | 下一题：0，音频是提前合成的。追问：BreezeTTS2 0.2 秒；IndexTTS 2 两个字的接话 1.4 秒，一整句问句 4 秒 | 语音线 |
| 网络和播放缓冲 | 没有测，估计 0.2 到 0.4 秒 | 语音线 |

加起来，候选人说完到听见第一个音（不含网络和播放缓冲）：

| 这一轮面试官要说什么 | 多久 |
| --- | --- |
| 下一题、重念题目（约一半的轮次） | 约 1.9 秒：停顿 0.84 秒，模型 1 秒，音频现成 |
| 追问，BreezeTTS2 | 约 2.1 秒 |
| 追问，IndexTTS 2 | 接话约 3.3 秒，问句约 7 秒 |
| 候选人其实没说完 | 模型 1.9 秒时回答 `wait`，接着听；候选人一直不出声，3.1 秒时这一轮结束，再问一次模型，约 4.1 秒听到 |

- 这些数字的前提是停顿一确认就调 `respond`（上面「候选人停了一下」的做法），不等这一轮结束。等结束再调要慢 1 秒左右。
- 「说完了没有」并进 `respond` 以后，停顿时只调一次模型。语音线原来的做法是同时调两次（一次判断说完没有，一次先写着追问），时间一样，每轮多花一次调用的钱。
- 用 IndexTTS 2 时追问前有几秒空白，是实时模式目前最大的体验问题。引擎这边已经把能做的做了（先出短接话、问句尽量短、一出句子就送合成）。剩下的办法在语音线的文档里：实时模式改用 BreezeTTS2（要 Ryan 定，它的权重限非商业使用）、问句在逗号处切开合成、这一轮一结束先播一个提前合成的语气词。
- 候选人网页线的第一版不走实时通道，按静音 2 秒判断说完，没有 `JudgeWanted` 也没有打断检测。那种接法下继续用 `respond`，不用改；估计下一题 3.5 到 4 秒，追问的问句 9 秒左右。

## 和逐题模式怎么选

| | 逐题模式 | 实时对话模式 |
| --- | --- | --- |
| 追问 | 提前写好的，每题默认最多 1 个 | 现场生成，贴着候选人刚说的话问 |
| 候选人反问、要求重复 | 只能重念题目 | 能回应 |
| 候选人停下来想词 | 等满静音时长 | 模型判断没说完就接着听 |
| 候选人打断面试官 | 不处理 | 知道候选人听到了哪，没听全就重念 |
| 模型多久做出决定 | 1.1 到 1.3 秒，有过渡语盖住 | 1.0 秒 |
| 需要现场合成语音 | 不需要 | 追问和回应需要 |
| 需要流式语音识别 | 不需要（可以面试后整段转写） | 需要 |
| 一场的模型费用 | 不到 0.02 元 | 0.01 到 0.05 元 |
| 现在能不能用 | 能 | 引擎和语音两侧都好了；候选人网页的实时通道（边说边传、边合成边播）还没有接 |

配置里的 `mode` 选 `conversational` 就是实时对话模式。两种模式用同一份出题结果，出题时不用区分。
