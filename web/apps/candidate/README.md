# 候选人面试页

候选人点开面试链接看到的网页。不用登录：链接里 `#` 后面的令牌就是凭证，只放在请求头里，不进地址的路径和查询串，也不存到本机。

流程：须知 → 同意事项 → 设备检测（摄像头、麦克风、扬声器、上行网速）→ 面试（面试官一句一句说，候选人答完静音几秒自动进入下一句）→ 结束页。全程录像，分片存在浏览器的 IndexedDB 里边录边传，断网和刷新都不丢。

录像分片里是候选人的脸和声音，传上去一片就从本机删一片。传不上去的也不留在设备上：服务端明确说这条链接不能用了（无效、过期、被撤销、面试被取消或删除），就把这条链接留在本机的分片删掉；打开任何一条面试链接时，顺手把别的面试留下的、超过 7 天的分片删掉（服务端默认面试结束 24 小时后就不收了）。网络不通、服务端临时出错不删，留着下次接着传。逻辑在 `src/lib/upload/leftovers.ts`。

面试结束后保存页上写着还剩多少没传、按现在的速度大约还要多久（上传器按最近几片算出每秒传多少）；估出来要一分钟以上，就明说网络上传比较慢、要等一会儿，不再说「一般不到一分钟」。

录像传不完整的时候不让候选人干等。面试结束后一段时间没有新的分片传来（默认 30 分钟），服务端就把已经收到的部分合并出来给 HR 看；候选人之后才回来，服务端说这一段已经合并了（`segment_closed`），页面就把本机剩下的那几片删掉。本机有一片没存下来、怎么重试都补不上的，页面告诉服务端「缺的补不上了」（`accept_missing`），服务端把缺口之前的部分合并出来，页面照常显示结束页。`pnpm e2e incomplete` 是这两种情况的测试。

面试到一半本机存不下录像了（磁盘满了、浏览器给的配额用完了），写不进 IndexedDB 的分片先留在内存里，上传器照样传走，录像不会出现缺口（`src/lib/upload/spill-chunk-store.ts`）。内存里最多留 64 MB，大约一刻钟的录像，超过了才丢；这时候刷新页面，内存里没传完的会丢。发生时记一条 `recording_error` 过程事件，带 `kept_in_memory: true`。

面试官的语音取的是压缩过的（取的时候带 `Accept: audio/mpeg`，服务端压成 MP3，体积是 WAV 的五分之一左右），候选人下行慢的时候少等几秒。万一有浏览器解不了，改取没压缩的再试一次，这一场之后都取没压缩的，记一条过程事件 `audio_format_fallback`。

页面自己出问题的时候不留一片空白。`index.html` 里自带一块不靠脚本的内容：脚本还没下完时显示「正在打开面试」，等了八秒还没出来就说一句网络慢并给一个刷新按钮；脚本没下下来，或者浏览器太旧跑不起来，就告诉候选人检查网络后刷新、还不行换浏览器或换设备。这一块的文字按浏览器的语言分中英文，写在 `index.html` 里的一小段脚本里（只用老浏览器也认识的写法，样式也是），页面一渲染出来它就被换掉。页面渲染到一半出错由 `src/components/CrashBoundary.tsx` 接住，显示「页面出了点问题，请刷新」：面试中出错时面试停在原地（不会在候选人看不见的地方接着收回答），记一条过程事件 `page_error`，刷新后检查设备接着面。页面要用的随机标识走 `src/lib/random-id.ts`，不直接用 `crypto.randomUUID`：用 http 打开的页面和旧浏览器里没有它，以前页面会直接白掉，现在能走到「这个浏览器不支持面试」的说明。

两件顺带做的事：设备检测时自己测一次上行网速，比录像的码率富余不到五成时，开始录像就把画面的码率降到这条网络装得下（最低 120 kbps，声音不降，`src/lib/recording/bitrate.ts`），并告诉候选人画面会糊一些；降到最低还装不下才提醒结束后要多等，都不拦着。这么做是因为录像传得比录得慢时，面试中服务端等不到回答的声音，只能按听到的半截来判断。实际用的码率记在过程事件 `interview_started` 里；点「开始面试」时申请屏幕常亮，手机不会在听题的时候自己锁屏（浏览器不给也照常面试，结果记进过程事件）；面试结束后录像还没传完的时候也留着，传完才松开，不然候选人放下手机等保存，手机一锁屏上传就停了。录像传不动了、又传动了、最后全部传完，也各记一条过程事件，HR 查录像为什么迟迟不出来时用得上。

同一条链接同时开在两个页面里（手机和电脑各开一个），只有一个页面在面试：后点「开始面试」或「继续面试」的那个接着面，前一个几秒之内停下面试和录制，把录下的传完，显示「面试已经在另一个页面里继续了」，并给一个「回到这个页面继续面试」的按钮（点了就重新载入，检查设备后接回来）。页面每次载入给自己起一个标识，随每个请求带给服务端（`X-Room-Page`，`src/lib/api/room-api.ts`），服务端在响应头里告诉它面试是不是在别处进行（响应头没到、请求被服务端以 `active_elsewhere` 拒绝时，页面也当作被告知了，不会说成链接失效）；只有正在面试的页面理会这个提醒，还在欢迎页和设备检测的不理会。停下来的页面记一条过程事件 `page_taken_over`。同一个浏览器里开两个标签页时，它们共用本机的录像队列，所以每一段都记着是哪个页面录的（`src/lib/upload/owned-chunk-store.ts`）：页面只收尾、只上传自己录的段，和录它的页面已经不在了的段（刷新、崩溃留下的）。页面在不在靠 Web Locks 判断（`page-presence.ts`），浏览器没有这个能力时都当作不在了。`pnpm e2e two-pages` 是这几种情况的测试。

页面的语言跟着面试的语言走：面试配成英文（`language` 是 `en`），从须知到结束页都是英文，同意事项也由后端按面试语言给；其余是中文。链接无效这类还不知道是哪场面试的页面，按浏览器的语言显示。文字都在 `src/text/`（`zh.ts`、`en.ts` 两份，结构必须一样，有测试检查英文那份里没有中文、两份的条目对得上），`@ai-interview/ui` 组件自带的文字通过 `UiTextProvider` 一起换。加一句新文案时两份都要加。

面试中被打断的两种情况都会停下来等候选人，计时不走，下一句也先不播：摄像头或麦克风断了（拔掉、被别的应用占用、来电话时系统把麦克风静音），提示「重新连接」；声音被系统整个停掉（来电话、切到别的应用、锁屏之后 AudioContext 不转了），页面先自己试着恢复，恢复不了就提示「继续面试」，候选人点一下再恢复（有的手机只在点击里才让声音恢复）。两种都记进过程事件 `recording_gap` 和 `device_recovered`，报告能看到哪一段录像没有声音。

## 怎么跑

```bash
scripts/dev.sh                                                # 仓库根目录：起开发数据库和后端（127.0.0.1:8080）
DATABASE_URL=$(scripts/dev-db.sh url) cargo run -p interview-room --example demo -- seed   # 造一场面试，打印链接
pnpm install          # 在 web/ 下
pnpm dev              # http://localhost:5174/i/#<上面打印的令牌>
```

`pnpm dev` 把 `/api` 转给 `AI_INTERVIEW_API_URL`（默认 `http://127.0.0.1:8080`）。`demo seed` 造的面试用合成的题目和提示音，不用先走出题和语音合成，详见 `crates/interview-room/README.md` 的「本地联调」。

## 检查

```bash
pnpm typecheck
pnpm test             # 单元测试：静音检测、答题状态机、上传队列、接口客户端、面试编排、过程事件
pnpm e2e              # 浏览器端到端测试，自己起后端和开发服务器
```

端到端测试用真的 Chromium 加假的摄像头和麦克风（合成的正弦波，不含真人录音），对着真的后端跑，覆盖：完整走完一场、脚本没下完或没下下来或跑不起来时页面有提示、用 http 打开时说明原因、页面渲染出错时面试停住并能刷新接着面、面试官的语音是压缩后下发的、浏览器解不了压缩的语音时改取没压缩的、网速偏慢时的提醒、上行装不下配置的码率时画面降下来而录像不在本机积压、上传比录像慢时面试照常往下走、「还剩多少没传」算得准、保存页说了大约要等几分钟、录像传完之前屏幕常亮一直留着（`pnpm e2e slow-uplink`，用浏览器的调试接口限上行速度）、链接过期和撤销、拒绝权限、手动结束、答题中刷新后续面、断网后补传、接口重试、过程事件、声音被系统停掉之后的恢复、整场英文面试页面上没有中文、一直不出声时提醒一次再提前结束、几种手机尺寸下答题的按钮和倒计时都在第一屏、面试到一半链接被撤销、链接失效后清掉留在本机的录像、同一条链接开在两个页面里时面试换到后一个页面、实时对话从头走到尾（面试官现场追问的话取得到、播得出，停顿时先问服务端说完没有）、实时对话里候选人插话再刷新页面、实时对话里断网几秒加接口出错后面试照常走完、浏览器把录像录成 MP4（iPhone 和 Safari 是这种容器）时照样传、照样转写、合并出来能拖动。每个测试用 `demo seed` 造一场自己的面试，跑完用 `demo state` 到库里看对话记录、过程事件和录像。装了 ffprobe 时还会检查录出来的文件有画面有声音、时长盖住整场面试。

后端由 `e2e/backend.sh` 起：用开发数据库实例上单独的一个库 `ai_interview_e2e`（每次清空重建），数据放在临时目录，不碰平时开发用的库。需要本机有 Rust 工具链、PostgreSQL 和 Playwright 的 Chromium（`pnpm exec playwright install chromium`）；第一次跑要先编译后端。不调大模型，不花钱。实时对话的那几条（`e2e/realtime.spec.ts`）靠面试间自带的替身接话（`AI_INTERVIEW_ROOM_FAKE_LIVE_MODEL`，见 `crates/interview-room/README.md` 的「测试」）：它每道题追问一句固定的话，所以测的是页面和服务端在实时对话下接不接得上，面试官接得好不好要用下面的真模型看。CI 里的 `candidate-e2e` 跑的就是这一套，失败时的截图留在那次运行的附件里。

### 用真的语音识别和真的大模型跑

平时语音识别是假后端、大模型不调。想看真的效果（候选人说的话有没有被听对、模型会不会追问、等多久）：

```bash
eval "$(crates/interview-stt/scripts/fetch-sherpa-lib.sh --extract)"   # 只有云端容器需要
crates/interview-stt/scripts/download-models.sh
export AI_INTERVIEW_STT_MODEL_DIR=~/.cache/ai-interview/stt-models
E2E_REAL=1 E2E_SPEECH_WAV=<一段有人说话的 WAV> pnpm e2e
```

这时只跑 `e2e/real.spec.ts`：假麦克风循环放那段 WAV（后面自动补 7 秒安静），后端带着 `sherpa` 特性编译，读环境里的 `DEEPSEEK_API_KEY`。一场三道题的面试模型费用在几分钱以内，CI 不跑。跑完会打印每一句的起止时间、回答有没有文字、候选人答完多久面试官开口。录音自己准备，不放进仓库：识别模型的包里有几段示例（`test_wavs/`），想让回答切题可以用任何本地的语音合成工具现做一段。

2026-11-13 在云端容器里实测（Chromium 录的声音，X-ASR 识别，deepseek-flash 判断）：

- 第一题只讲「我们团队做了什么」，模型判为偏弱并追问「你自己做了什么」；接着讲了本人负责的部分和具体数字，模型判为好，进入下一题。答非所问的回答被判为差，连着三题都这样时面试提前结束。
- 候选人停下来满静音时长后，过渡语马上开始播（0.3 秒以内）；过渡语播完到下一句开口是 0.1 到 1 秒。转写加模型判断一共一两秒，大部分藏在过渡语后面。
- 识别出来的文字有个别同音字错误，没有影响模型的判断。

`real.spec.ts` 里还有一条实时对话的测试（`pnpm e2e -g 实时对话` 只跑它）：面试配成实时对话，面试官现场接话，跑完打印候选人说完到面试官开口的中位数和 p95，以及停顿时问了服务端几次、各是什么结论。加上 `AI_INTERVIEW_LOG=info` 能在输出里看到后端每一轮各段用了多久。实测的数字和说明在 `crates/interview-room/README.md` 的「实时对话」。云端没有真的语音合成，量出来的不含合成时间。

## 长时间面试

真的面试有二三十分钟，平时的浏览器测试每场只有十几秒，看不出慢慢攒起来的问题。`e2e/soak.spec.ts` 让一场面试一直面到设的分钟数，每半分钟记一次页面用了多少内存、本机还留着几片录像、服务端收到了几片，最后看合并出来的录像是不是和面试一样长：

```bash
E2E_SOAK_MINUTES=15 pnpm e2e soak
```

不设这个变量就跳过，CI 不跑。要本机有 ffprobe。

2026-11-16 在云端容器里跑了 25 分钟的一场：页面占的内存一直在 16.7 到 17.1 MB 之间，页面元素和事件监听的个数没有变；本机留着的录像始终只有刚录下的 0 到 1 片；合并出来的录像 25.1 分钟、59.6 MB、1479 片，和面试时长对得上，播放器读得出时长。

## 面试页的版面

手机上浏览器的地址栏和工具栏要占掉一截，看得到的高度比屏幕矮不少：iPhone 13 到 15 的 Safari 是 390×664，iPhone SE 是 375×548。候选人答题时手不在屏幕上，「我答完了」、倒计时和提示必须在第一屏里。面试页按窗口大小分三种排法（`src/lib/flow/layout.ts`，样式在 `src/app.css`）：

- 够高（820 以上，电脑和少数大屏手机）：从上到下一列，面试官、提示、题目、自己的画面。
- 手机浏览器里常见的高度：面试官在左，自己的画面和音量在右，下面是提示和题目。按钮贴在屏幕底部，题目太长时从按钮下面滚过去。
- 手机横过来：面试官和自己的画面在左，提示和题目在右，按钮排成一行。

给候选人的提示（「说完了吗？还想补充就继续说」这类）单独占一行、可以折行。面试官头像下面的小标签不折行，只写「正在听」这样的短状态，长句子放进去会伸到屏幕外面。

改了面试页上的东西，跑 `pnpm e2e layout` 看几种尺寸下有没有东西掉到第一屏外面或者伸出屏幕。

## 键盘和读屏软件

候选人里会有只用键盘、或者靠读屏软件（VoiceOver、TalkBack、NVDA）的人。页面上守这几条：

- 换到新的一页，焦点放到这一页的一级标题上（`src/lib/flow/page-heading.ts`，在 `App.tsx` 里换页时调）。读屏软件会把标题读出来，候选人知道换了页面；再按 Tab 就是这一页的第一个按钮。所以**每一页都要有一个 `h1`**。面试中那一页画面上不放标题，用只给读屏软件的（`oil-sr-only`）。
- 浏览器标签页上的名字跟着页面换（「设备 · AI 面试」）。欢迎页的标题里有候选人的名字，标签页上用步骤的名字，不带人名。
- 顶上的步骤条用 `src/components/StepBar.tsx`，不直接用设计系统的 `Steps`：窄的版式里步骤的名字不显示，读屏软件只读得到「1、2、3、4」，`StepBar` 把整条读成「第 2 步，共 4 步：同意」。
- 整个页面在 `main` 里。
- 会变的状态（设备检测的结果、轮到候选人了没有）放在 `role="status"` 的元素里，这个元素一直在页面上、只换里面的字，读屏软件才会读。要马上知道的（设备断了、声音被系统停了）用设计系统的 `Banner tone="danger"`，它是 `role="alert"`。
- 面试中给候选人的提示有两份：画面上那一行给眼睛看（`aria-hidden`），旁边一行只给读屏软件（`src/lib/interview/announce.ts` 决定念什么）。分开是因为面试官说话的时候读屏软件不能出声，不然题目的开头被盖住；轮到候选人、面试停住、要等一等的时候才念。面试官的语音放不出来只能看文字时，把那句话的文字也念出来。在面试页上加新的提示，想一下它出现时面试官是不是正在说话。面试官头像下面的小标签（「正在提问」「正在听」）因此不让读屏软件念（`InterviewerPresence` 传 `announce={false}`）。

`pnpm e2e a11y` 不碰鼠标、只按键盘走完一场面试，每一页查焦点、标题、步骤条和标签页的名字。它没有真的读屏软件，查的是读屏软件靠的那几样东西；真的读屏软件要在真机上试（`docs/room/real-device.md` 第八部分）。

## 深色模式

页面只有浅色的样子，不跟着手机的深色模式变（面试中那一页的深色舞台是画出来的）。有的安卓浏览器在深色模式下会自己把浅色的网页变暗，变出来的颜色没人设计过。所以页面声明了自己只有浅色（`color-scheme: only light`），写了两处：`index.html` 里的 `meta` 管样式下完之前，`src/app.css` 里的 `html:root` 管之后（设计系统里写的是 `light`，样式里的会盖掉 `meta`，所以两处都要）。

`pnpm e2e dark-mode` 查的是系统是深色时页面自己的颜色没变、这个声明还在。浏览器自己变暗那一半在云端的 Chromium 里开不出来，要在真机上看（`docs/room/real-device.md` 第九部分）。在页面里加 `prefers-color-scheme` 的样式之前先想清楚：现在没有，这条测试会拦。

## 目录

- `src/lib/`：不依赖页面的逻辑，都有单元测试。`vad`（静音检测）、`turn`（一道题的状态机；静音从声音停下的那一刻算起，不含静音检测确认停止用的 0.4 秒；实时对话里服务端判断过这次停顿的，说完了就少等、没说完就多等）、`interview`（逐题编排；实时对话里候选人一停顿就先传一片录像、问服务端「说完了吗」；面试官说话时听到候选人出声先停下，接着说就改成听候选人说，只是咳嗽一声就接着播）、`recording` 和 `upload`（分片录制、断点续传、清掉传不上去的分片）、`media`（采集、混音、屏幕常亮、盯着声音有没有被系统停掉）、`events`（过程事件）、`api`（面试间接口，用 `@ai-interview/api-client` 生成的类型）、`flow`（链接、浏览器能力、上行测速、面试页按屏幕高度选哪种版面）。
- `src/text/`：页面上的文字，中英两份。页面用 `useText()` 取，不直接写死。
- `src/session/interview-session.ts`：把上面这些串成一场面试，页面只订阅它的状态。
- `src/pages/`、`src/components/`：页面，用 `@ai-interview/ui` 的组件。
- `e2e/`：端到端测试。后端的实现在 `crates/interview-room`。

接口约定见 `docs/architecture/api.md` 的「面试间协议」。

浏览器测试只有 Chromium 加假的摄像头和麦克风。手机上（尤其是 iPhone 和微信里）的权限弹窗、录像格式、自动播放、来电话和锁屏，要拿真机照 `docs/room/real-device.md` 走一遍（issue #15）。
