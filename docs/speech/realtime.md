# 实时对话：候选人说完到听见面试官，要多久

实时对话模式下，面试官的追问和回应是现场生成、现场合成的。这份文档回答一个问题：候选人最后一个字说完，到听见面试官下一句的第一个音，中间要多久，能不能接近当面对话。

引擎那一侧的做法（每轮怎么调模型、上下文怎么管）见 `crates/interview-engine/docs/realtime.md`。这里写语音这一侧：分段实测、整条链路加起来的数字、怎么缩短、三条线怎么接。

## 结论

1. **能做。** 大约一半的轮次是「进入下一题」，音频是提前合成的，候选人说完 2 秒左右就能听到，和用哪个合成引擎无关。
2. **现场合成的追问，快慢取决于合成引擎。** 用 BreezeTTS2 也是 2 秒左右。用 IndexTTS 2（现在的默认），两个字的接话 3 秒左右能听到，问句要到 7 秒左右；把问句切开合成能提前到 4 秒多（还没有实现），中间靠提前合成的语气词来填。
3. **最大的一段不是模型，是等候选人停下来。** 确认停顿要 0.6 到 0.8 秒，省不掉太多：再短就会把换气当成说完。模型的 1 秒可以和它并行。
4. **需要 Ryan 定的一件事**：实时模式要不要改用 BreezeTTS2。它首块 0.2 秒，但权重限非商业使用（见 `tts/README.md`），音色和 IndexTTS 克隆出来的也不完全一样，要听过再定。不改的话实时模式也能用，追问前的等待长一些。
5. **第一版比上面慢。** 候选人网页线的第一版沿用一句一句推进的做法，不做语义判停和边合成边播，估计下一题 3.5 到 4 秒、追问的问句 9 秒左右，见「第一版先怎么做」。上面的 2 秒是下一步接上实时通道以后的数字。

## 分段实测

除了语音合成，都是 2026-11-13 在云端容器（4 核）里测的，含到 DeepSeek 的网络往返。语音合成是同一天在 M3 Max 的 Mac 上测的。

| 环节 | 中位数 | 慢的时候 | 怎么测的 |
| --- | ---: | ---: | --- |
| 1. 发现候选人停下来了，这段话的文字定稿 | 0.84 秒 | 0.85 秒 | 真识别模型，按真实时间 20 毫秒一帧地喂，10 遍。停顿阈值用默认的 600 毫秒 |
| 　停顿阈值调到 300 毫秒 | 0.62 秒 | 0.62 秒 | 同上，10 遍 |
| 2. 大模型判断「说完整了没有」 | 0.89 秒 | 1.33 秒（P95） | deepseek-flash，思考关闭，24 次，24 次都判对 |
| 3. 大模型写出追问的第一个分句 | 1.05 秒 | 1.21 秒（P95） | deepseek-flash，思考关闭，流式，8 次 |
| 　思考强度 low | 1.82 秒 | 1.95 秒（P95） | 同上 |
| 　思考强度 high | 1.76 秒 | 2.15 秒（P95） | 同上 |
| 　思考强度 max | 1.89 秒 | 2.07 秒（P95） | 同上 |
| 4. 语音合成出第一块音频：BreezeTTS2 | 0.16 到 0.27 秒 | | 和句子长短无关。每句跑三次取中位数，最大值比中位数最多高 5% |
| 　IndexTTS 2，两个字的接话 | 1.44 秒 | | 同上 |
| 　IndexTTS 2，一句追问（约 6 秒的话） | 3.95 秒 | | 同上。IndexTTS 2.5 是 3.26 秒 |
| 5. 网络和播放缓冲 | 没有测 | | 候选人网页的实时通道还没有做。估计 0.2 到 0.4 秒：音频块从 Mac 到服务器再到浏览器，加上浏览器播放前攒的一小段 |

说明：

- 第 1 段包含了转写：识别是边听边做的，停顿一确认，这一段的文字就定下来了，不用另外等。0.84 秒里 0.6 秒是在等停顿，其余是停顿检测本身的滞后和识别最后一段话的时间。`docs/speech/stt.md` 里写的 0.7 秒是按喂进去的音频算的，这里按真实时间算，多出来的就是识别用的时间。
- 第 2 段和第 3 段可以同时做，见下一节。
- 思考打开以后第一个分句要多等 0.7 到 0.8 秒，三档强度差别不大。实时模式建议关闭思考，和引擎线的结论一致。
- 语音合成的完整数字（四种长度、四种配置）在 `tts/worker/README.md`。测的时候 Mac 不是空闲的，IndexTTS 的数字偏慢。

## 整条链路

用 `crates/interview-stt/examples/realtime_latency.rs` 把真识别模型和真大模型串起来跑，按真实时间喂音频，时间都从话音真正落下的那一刻算起。各跑 10 遍：

| 时刻 | 默认（停顿 600 毫秒） | 停顿 300 毫秒 |
| --- | ---: | ---: |
| 发现停顿，文字定稿，开始问大模型 | 0.84 秒 | 0.62 秒 |
| 「说完整了没有」的判断回来 | 1.80 秒（最慢 2.02） | 1.70 秒（最慢 1.82） |
| 这一轮结束：判断说完整了 | 和判断回来同时 | 同左 |
| 这一轮结束：判断没说完整，或者判断没回来 | 3.10 秒 | 3.12 秒 |
| 追问的第一个分句出来：发现停顿就开始写 | 1.70 秒（最慢 1.92） | 1.49 秒（最慢 1.81） |
| 追问的第一个分句出来：等这一轮结束再写 | 2.4 到 2.9 秒（判断说完整了时） | 2.0 到 2.9 秒 |

再加上语音合成的首块，候选人说完到听见第一个音（不含第 5 段的网络和播放缓冲）：

| 这一轮面试官要说什么 | BreezeTTS2 | IndexTTS 2 |
| --- | ---: | ---: |
| 下一题（提前合成的，约一半的轮次） | 约 2 秒 | 约 2 秒 |
| 追问或回应，先说一句两个字的接话 | 约 2 秒 | 接话约 3.1 秒；问句约 7 秒 |
| 追问或回应，不单独说接话，问句在逗号处切开先合成前半句 | 用不着 | 约 4 到 4.7 秒听到问句，之后不断（没有实现，按分段的数字算的） |

这些数字是这样来的：

- 「下一题」和 BreezeTTS2 的追问都卡在同一个地方：要等「说完整了」的判断回来（1.8 秒）才能出声，文字和音频在这之前已经准备好了。
- IndexTTS 2 一次只合成一句。第一个分句 1.70 秒出来，接话合成 1.44 秒，3.1 秒听到；问句排在后面再合成 3.95 秒，7 秒左右才听到。接话只有一秒长，所以它播完以后有 3 秒左右的空白。这和引擎线文档里估计的一致。
- 候选人说了半句停下来想词，判断是「没说完」，这一轮要等满 3 秒才结束。这是有意的：宁可多等，不抢话。

## 怎么缩短

按效果从大到小：

| 办法 | 效果 | 代价和没验证的地方 |
| --- | --- | --- |
| **发现停顿就开始写回答**，不等这一轮结束。候选人接着说就作废 | 第一个分句从 2.4 到 2.9 秒提前到 1.7 秒，省约 1 秒。已实测 | 作废的那次调用白花钱，一次约一厘钱 |
| **实时模式用 BreezeTTS2** | 追问的问句从 7 秒降到 2 秒 | 非商业许可；音色和 IndexTTS 的克隆有差别，同一场面试里提前合成的题目也要用它，不然听起来像换了个人 |
| **这一轮一结束就播一个提前合成的语气词**（「嗯。」） | 用 IndexTTS 时，1.8 秒就有声音，盖住合成的等待 | 要挑听起来不像要换题的词。逐题模式已经这么做了（`listen.ack`） |
| **问句在逗号处切开合成**（只对 IndexTTS 有用） | 前半句 1.9 到 2.7 秒合成完，比整句早 1.3 到 1.7 秒；问句从 7 秒提前到 4 秒多 | 两半接起来比整句长 1.1 秒；语调接不接得上还没有人听过。没有实现 |
| **把「说完整了没有」并进引擎的那次调用**：第一行除了追问、回应、下一题，再加一种「候选人还没说完，接着听」 | 少调一次模型；引擎知道题目和提纲，判断更准 | 引擎线的提示词要改，要重新实测 |
| **停顿阈值从 600 毫秒调到 300 毫秒** | 省 0.2 秒 | 换气会把一句话切开，判断请求变多。只用拼接的示例录音测过，真人说话的效果没测 |
| IndexTTS 把参考音色的编码存下来复用 | 可能缩短每条请求 1.4 秒的固定开销 | 没有验证 |

前两条加起来，实时模式的典型延迟是 2 秒左右。当面对话里对方想一下再接话，差不多也是这个节奏。

## 三条线怎么接

语音线给出的东西都在 `interview-stt` 和 `interview-tts` 里，用法见 `docs/speech/stt.md` 的「实时对话：一轮回答和打断」。面试间（候选人网页线）把它们和引擎串起来：

```text
浏览器麦克风（16 kHz PCM16，20 到 100 毫秒一帧）
   │  二进制帧
   ▼
TurnListener::push ──► Partial ──────────────► 发 transcript（final 为 false）
                  ──► Segment ──────────────► 发 transcript（final 为 true），存下逐字时间戳
                  ──► JudgeWanted ──────────► 开始调引擎（见下面），回来后调 verdict
                  ──► Ended { transcript } ─► 候选人这一轮定下来，记进 interview_turns

引擎 live::respond ──► Speak { key, text } ──► Synthesizer::synthesize_stream ──► 发 speak_begin 和音频帧
                  ──► Play { utterance } ───► 发 speak_begin（mode 为 url）

面试官说话期间：
BargeInDetector::push ──► Detected ─────────► 发 interrupt，停掉合成，into_turn 接着听
```

几个要对齐的地方：

1. **不说话也要发静音帧。** `TurnListener` 的时间按收到的音频走，浏览器停发，这一轮就不会结束。
2. **`JudgeWanted` 怎么回答，有两种做法。** 简单的：单独调一次模型问「说完整了没有」（提示词在 `realtime_latency.rs` 里，实测 24 次都对），同时先调 `live::respond`，候选人接着说就把两个都取消。更好的：引擎的第一行加一种「接着听」的动作，一次调用同时回答「说完没有」和「怎么接」。前一种不用改引擎，可以先用。
3. **`respond` 的结果要等 `Ended` 才能用。** 先调是为了省时间，但候选人可能接着说。`Speak` 出来的文字可以先送去合成，音频等 `Ended` 之后再发给浏览器。
4. **下行音频的采样率看合成引擎**：IndexTTS 是 22050 Hz，BreezeTTS2 是 24000 Hz。`speak_begin` 里的 `content_type` 要按实际的填（`audio/pcm;rate=22050` 或 `rate=24000`），接口文档里的例子写的是 24000，不要写死。每块音频自己带着采样率（`Audio::sample_rate()`）。
5. **打断以后引擎要知道面试官那句话实际播到了哪里。** 语音线给出发现打断的时刻（`BargeInDetector::detected_at_ms()`）和候选人已经说的字；浏览器在 `playback` 消息里报播到了哪里。引擎线的文档里已经留了这个口子。
6. **回声。** 浏览器取麦克风时要打开回声消除（`getUserMedia` 的 `echoCancellation: true`），建议候选人戴耳机。`BargeInDetector::interviewer_says` 告诉它面试官正在说什么，漏进麦克风的同样的字不算打断，这是第二道保险，不是替代。
7. **一台 Mac 同时只能合成一句。** 模型一次跑一条，两场实时面试同时进行时现场合成会排队。实时模式先按一台 Mac 一场来用。

## 第一版先怎么做

候选人网页线定的第一版不走上面的实时通道，沿用逐题模式一句一句推进的 HTTP 协议：页面按静音判断候选人说完（阈值压到 2 秒左右），服务端用已经上传的录像分片转写，再调 `live::respond`，追问按句合成，一句一个完整的音频文件发给页面。好处是录制、断网重试、刷新续面都不用另做一套。`TurnListener` 和 `BargeInDetector` 留到下一步（语义判停和打断）再接。

按上面分段的数字估，这种做法下候选人说完到听见面试官（没有实测，候选人网页线合并后会在真浏览器里量）：

| 这一轮面试官要说什么 | 估计 |
| --- | --- |
| 下一题（提前合成的） | 3.5 到 4 秒：静音 2 秒，最后一段录像上传和转写约 0.5 秒，模型约 1 秒 |
| 追问，IndexTTS 2 | 接话约 5 秒，问句约 9 秒 |

这种做法下要注意两点：

- **一句一个完整文件时，BreezeTTS2 不占便宜。** 它快在第一块出得早，整句合成完反而比 IndexTTS 慢：一句追问 BreezeTTS2 要 5.15 秒，IndexTTS 2 是 3.95 秒，IndexTTS 2.5 是 3.26 秒。所以第一版里最快的是 IndexTTS 2.5，上面「实时模式用 BreezeTTS2」那一条要等音频能边合成边播才成立。
- **候选人说完时要把录像的最后一段马上交上来。** 录像默认 5 秒切一片，不主动交的话，最后几个字要等这一片录满才到服务端。

## 没有测和没有做的

- 第 5 段（网络和播放缓冲）没有测，要等候选人网页的实时通道做出来，在真的浏览器里量。
- 整条链路没有用真人的回答测过。示例录音是几句不相干的话拼起来的，「说完整了没有」的判断在它上面一半说完整、一半说没说完，所以上面分两种情况列。用像样的回答文字单独测这个判断时 24 次都对。
- 真实麦克风和扬声器下的回声、背景噪音、口音，都没有测。
- 语音合成读出来的字对不对没有核对过，也没有人听过三个引擎现场合成的追问。试听文件在 Mac 上。
- 没有把真识别、真大模型、真合成放在一起跑：前两个在云端，合成在 Mac 上。表里是分别测了以后加起来的。
- Rust 这边的 worker 客户端（`WorkerBackend`）没有连过真的 worker，Mac 上的测量用的是 Python 脚本。协议是同一份，假 worker 的测试是过的。

## 重现

```bash
# 整条链路（云端容器可以跑，读 DEEPSEEK_API_KEY，每遍不到一分钱）
eval "$(crates/interview-stt/scripts/fetch-sherpa-lib.sh)"
export AI_INTERVIEW_STT_MODEL_DIR=~/.cache/ai-interview/stt-models
cargo run --release -p interview-stt --features sherpa --example realtime_latency -- 回答.wav --runs 10
cargo run --release -p interview-stt --features sherpa --example realtime_latency -- 回答.wav --runs 10 --min-silence-ms 300

# 只测识别这一侧（不调大模型）
cargo test --release -p interview-stt --features sherpa --test sherpa_live -- --ignored --nocapture --test-threads=1
```

`回答.wav` 用任意一段中文录音。上面的数字用的是识别模型自带的四段示例录音接在一起，每段之间隔 0.25 秒，共 30 秒。语音合成的测法见 `tts/worker/README.md`。
