# 实时对话：候选人说完到听见面试官，要多久

实时对话模式下，面试官的追问和回应是现场生成、现场合成的。这份文档回答一个问题：候选人最后一个字说完，到听见面试官下一句的第一个音，中间要多久，能不能接近当面对话。

引擎那一侧的做法（每轮怎么调模型、上下文怎么管）见 `crates/interview-engine/docs/realtime.md`。这里写语音这一侧：分段实测、整条链路加起来的数字、怎么缩短、三条线怎么接。

## 结论

1. **能做。** 大约一半的轮次是「进入下一题」，音频是提前合成的，候选人说完 2 秒左右就能听到，和用哪个合成引擎无关。
2. **现场合成的追问，快慢取决于合成引擎。** 用 BreezeTTS2 也是 2 秒出头。用 IndexTTS 2（现在的默认），两个字的接话 3.5 秒左右能听到，问句要到 7 秒多；不说接话直接合成问句是 6 秒左右，把问句切开合成能提前到 4 秒多（还没有实现），中间靠提前合成的语气词来填。
3. **2 秒里一半是等候选人停下来，一半是引擎做决定。** 确认停顿要 0.6 到 0.8 秒，省不掉太多：再短就会把换气当成说完。引擎 1 到 1.2 秒定下来候选人说完没有、怎么接，追问的文字紧跟着就出来。
4. **候选人话说到一半停下来，引擎会接着听。** 候选人一直不再出声的话，3.1 秒时面试官接话。实测 60 遍，引擎对「说完了没有」的判断都对。
5. **需要 Ryan 定的一件事**：实时模式要不要改用 BreezeTTS2。它首块 0.2 秒，但权重限非商业使用（见 `tts/README.md`），音色和 IndexTTS 克隆出来的也不完全一样，要听过再定。不改的话实时模式也能用，追问前的等待长一些。
6. **第一版比上面慢。** 候选人网页线的第一版沿用一句一句推进的做法，不做语义判停和边合成边播。在真浏览器里实测，下一题 3.3 到 3.5 秒（P95 3.9 秒）；追问要再加整句的合成时间，估计 7 到 9 秒，见「第一版先怎么做」。上面的 2 秒是下一步接上实时通道以后的数字。

## 分段实测

除了语音合成，都是 2026-11-13 在云端容器（4 核）里测的，含到 DeepSeek 的网络往返。语音合成是同一天在 M3 Max 的 Mac 上测的。

| 环节 | 中位数 | 慢的时候 | 怎么测的 |
| --- | ---: | ---: | --- |
| 1. 发现候选人停下来了，这段话的文字定稿 | 0.84 秒 | 0.85 秒 | 真识别模型，按真实时间 20 毫秒一帧地喂，10 遍。停顿阈值用默认的 600 毫秒 |
| 　停顿阈值调到 300 毫秒 | 0.62 秒 | 0.62 秒 | 同上，10 遍 |
| 2. 引擎定下来候选人说完没有、怎么接（一次调用的第一行） | 1.0 到 1.2 秒 | 1.4 秒 | deepseek-flash，思考关闭，`live::respond_with` 带 `paused: true`，60 次，都判对 |
| 3. 追问的文字出来 | 比第 2 段晚不到 0.1 秒 | 0.2 秒 | 同上里是追问的 20 次。接话和问句都写完比第 2 段晚 0.13 秒 |
| 　思考打开（low、high、max） | 多 0.7 到 0.8 秒 | | 引擎改接口之前单独测的：只写追问第一个分句，关闭时 1.05 秒，三档 1.76 到 1.89 秒 |
| 4. 语音合成出第一块音频：BreezeTTS2 | 0.16 到 0.27 秒 | | 和句子长短无关。每句跑三次取中位数，最大值比中位数最多高 5% |
| 　IndexTTS 2，两个字的接话 | 1.44 秒 | | 同上 |
| 　IndexTTS 2，一句追问（约 6 秒的话） | 3.95 秒 | | 同上。IndexTTS 2.5 是 3.26 秒 |
| 5. 网络和播放缓冲 | 没有测 | | 候选人网页的实时通道还没有做。估计 0.2 到 0.4 秒：音频块从 Mac 到服务器再到浏览器，加上浏览器播放前攒的一小段 |

说明：

- 第 1 段包含了转写：识别是边听边做的，停顿一确认，这一段的文字就定下来了，不用另外等。0.84 秒里 0.6 秒是在等停顿，其余是停顿检测本身的滞后和识别最后一段话的时间。`docs/speech/stt.md` 里写的 0.7 秒是按喂进去的音频算的，这里按真实时间算，多出来的就是识别用的时间。
- 第 2 段和第 3 段是同一次模型调用：第一行是决定，后面是要说的话。早先的做法是同时调两次模型（一次判断说完没有，一次先写着追问），引擎线把判断并进来以后只调一次，时间差不多，判断更准，见 `crates/interview-engine/docs/realtime.md`。
- 思考打开以后要多等 0.7 到 0.8 秒，三档强度差别不大。实时模式建议关闭思考，和引擎线的结论一致。
- 语音合成的完整数字（四种长度、四种配置）在 `tts/worker/README.md`。测的时候 Mac 不是空闲的，IndexTTS 的数字偏慢。

## 整条链路

用 `crates/interview-stt/examples/realtime_latency.rs` 把真识别模型和真的面试引擎串起来跑，接法和面试间要用的一样：按真实时间喂音频，停顿一确认就带着 `paused: true` 调 `live::respond_with`，引擎的决定一出来就告诉 `TurnListener`。时间都从话音真正落下的那一刻算起。

声音是示例录音，停顿什么时候被发现、识别慢多少都是真的。示例录音的内容和题目无关，所以最后一次停顿时交给引擎的文字是另外写的三段回答：一段说完整的自我介绍、一段说完了但很空泛的、一段说到一半的（停在「嗯，那个」上）。每种 10 遍，中位数（括号里是最慢的一遍）：

| 时刻 | 说完整了，引擎进入下一题 | 说完了但空泛，引擎追问 | 话说到一半 |
| --- | ---: | ---: | ---: |
| 发现停顿，文字定稿，开始问引擎 | 0.83 秒 | 0.84 秒 | 0.84 秒 |
| 引擎的决定出来 | 2.02 秒（2.17） | 1.96 秒（2.21） | 1.86 秒（2.08），接着听 |
| 这一轮结束 | 2.04 秒 | 1.98 秒 | 3.10 秒 |
| 面试官的第一句话出来 | 2.04 秒（2.18），音频是提前合成的 | 2.00 秒（2.33），是一句很短的接话 | 3.10 秒（3.27） |
| 追问的问句出来 | | 2.05 秒 | |

- 引擎的 60 次决定都对：说完整的 20 次里 19 次下一题、1 次追问，空泛的 20 次都追问，说到一半的 20 次都接着听。（空泛的那一种跑了两批共 20 遍，表里是带问句时间的那一批；另外两种各有 10 遍是下面停顿 300 毫秒的。）
- 「话说到一半」那一列的 3.10 秒是这样来的：引擎说接着听以后，马上用同样的文字再调一次引擎（这次不能再选接着听），先把话备着。候选人一直没出声，3.10 秒时这一轮结束，备好的话正好能用。不提前备、等这一轮结束了才调引擎的话是 4.09 秒（最慢 4.35）。
- 停顿阈值从 600 毫秒调到 300 毫秒：发现停顿 0.62 秒，说完整了的那种面试官的话 1.66 秒出来（最慢 1.82），省 0.4 秒；话说到一半的不变（3.12 秒）。

再加上语音合成的首块，候选人说完到听见第一个音（不含第 5 段的网络和播放缓冲）：

| 这一轮面试官要说什么 | BreezeTTS2 | IndexTTS 2 |
| --- | ---: | ---: |
| 下一题（提前合成的，约一半的轮次） | 约 2 秒 | 约 2 秒 |
| 追问或回应，先说一句两个字的接话 | 约 2.2 秒，接话和问句连着 | 接话约 3.5 秒；问句约 7.5 秒 |
| 追问或回应，不说接话，直接合成问句 | 用不着 | 约 6 秒 |
| 追问或回应，不说接话，问句在逗号处切开先合成前半句 | 用不着 | 约 4 到 4.8 秒听到问句，之后不断（没有实现，按分段的数字算的） |
| 候选人话说到一半，之后一直没出声 | 约 3.3 秒 | 提前合成的 3.1 秒；现场的接话约 4.6 秒 |

这些数字是这样来的：

- 「下一题」和 BreezeTTS2 的追问都卡在同一个地方：要等引擎的决定（2 秒）。决定一出来，下一题的音频是现成的，BreezeTTS2 的第一块 0.2 秒就有。
- IndexTTS 2 一次只合成一句。接话的文字 2.0 秒出来，合成 1.5 秒，3.5 秒听到；问句的文字 2.05 秒就有了，但要排在接话后面，再合成 3.95 秒，7.5 秒左右才听到。接话只有一秒长，所以它播完以后有 3 秒左右的空白。不说接话的话问句 2.05 秒开始合成，6 秒听到，中间是 4 秒的安静。
- 候选人说了半句停下来想词，引擎说接着听，这一轮要等满 3 秒才结束。这是有意的：宁可多等，不抢话。

## 怎么缩短

按效果从大到小：

| 办法 | 效果 | 代价和没验证的地方 |
| --- | --- | --- |
| **停顿一确认就调引擎**，不等这一轮结束。候选人接着说就作废 | 省约 1 秒。上面的数字都是这样量的 | 作废的那次调用白花钱，一次不到一厘钱 |
| **引擎说接着听以后，马上再调一次把话备好** | 候选人不再出声时，面试官的话从 4.1 秒提前到 3.1 秒。已实测 | 多一次调用；候选人接着说就作废。这一轮结束时的文字和备的时候不一样也要作废重来 |
| **实时模式用 BreezeTTS2** | 追问的问句从 7 秒多降到 2 秒出头 | 非商业许可；音色和 IndexTTS 的克隆有差别，同一场面试里提前合成的题目也要用它，不然听起来像换了个人 |
| **这一轮一结束就播一个提前合成的语气词** | 用 IndexTTS 时，2 秒就有声音，盖住合成的等待 | 要挑听起来不像要换题的词，而且不能是单独一句「嗯。」「嗯嗯。」：IndexTTS 读纯语气词不稳，「好的。」「明白。」是稳的（见 `tts/worker/README.md` 的「很短的接话读得稳不稳」）。逐题模式已经这么做了（`listen.ack`） |
| **用 IndexTTS 时不说接话，直接合成问句** | 问句从 7.5 秒提前到 6 秒 | 前面 4 秒完全安静，要配上面那个提前合成的语气词才行 |
| **问句在逗号处切开合成**（只对 IndexTTS 有用） | 前半句 1.9 到 2.7 秒合成完，比整句早 1.3 到 1.7 秒；问句从 6 秒提前到 4 秒多 | 两半接起来比整句长 1.1 秒；语调接不接得上还没有人听过。没有实现 |
| **停顿阈值从 600 毫秒调到 300 毫秒** | 说完整了的那种省 0.4 秒 | 换气会把一句话切开，判断请求变多。只用拼接的示例录音测过，真人说话的效果没测 |
| IndexTTS 把参考音色的编码存下来复用 | 可能缩短每条请求 1.4 秒的固定开销 | 没有验证 |

第一条加上 BreezeTTS2，实时模式的典型延迟是 2 秒左右。当面对话里对方想一下再接话，差不多也是这个节奏。

## 三条线怎么接

语音线给出的东西都在 `interview-stt` 和 `interview-tts` 里，用法见 `docs/speech/stt.md` 的「实时对话：一轮回答和打断」。面试间（候选人网页线）把它们和引擎串起来：

```text
浏览器麦克风（16 kHz PCM16，20 到 100 毫秒一帧）
   │  二进制帧
   ▼
TurnListener::push ──► Partial ──────────────► 发 transcript（final 为 false）
                  ──► Segment ──────────────► 发 transcript（final 为 true），存下逐字时间戳
                  ──► JudgeWanted ──────────► 带 paused: true 调引擎，决定一出来就调 verdict
                  ──► Ended { transcript } ─► 候选人这一轮定下来，记进 interview_turns

引擎 live::respond_with ──► Action { action } ──► 是接着听就 verdict(revision, false)，别的 verdict(revision, true)
                       ──► Speak { key, text } ► Synthesizer::synthesize_stream ──► 发 speak_begin 和音频帧
                       ──► Play { utterance } ─► 发 speak_begin（mode 为 url）

面试官说话期间：
BargeInDetector::push ──► Detected ─────────► 发 interrupt，停掉合成，into_turn 接着听
```

几个要对齐的地方：

1. **不说话也要发静音帧。** `TurnListener` 的时间按收到的音频走，浏览器停发，这一轮就不会结束。
2. **`JudgeWanted` 来了就调引擎。** 带着 `TurnContext { paused: true, .. }` 调 `live::respond_with`，一次调用同时回答「说完没有」和「怎么接」。在 `sink` 里收到 `LiveEvent::Action` 的那一刻就调 `turn.verdict`，不要等整次调用返回：决定是接着听就传 `false`，别的传 `true`。候选人接着说了（又来了 `SpeechStarted`），这次调用作废。
3. **`respond_with` 的结果要等 `Ended` 才能用。** 先调是为了省时间，但候选人可能接着说。`Speak` 出来的文字可以先送去合成，音频等 `Ended` 之后再发给浏览器；返回的 `state` 也是真用上了才存。
4. **引擎说接着听以后，先把下一句备好。** 马上用同样的文字、`paused: false` 再调一次。候选人一直不出声，`Ended` 来的时候话已经备好；候选人接着说了，或者 `Ended` 里的文字和备的时候不一样，就丢掉重来。`realtime_latency.rs` 是这几条接起来的完整例子。
5. **下行音频的采样率看合成引擎**：IndexTTS 是 22050 Hz，BreezeTTS2 是 24000 Hz。`speak_begin` 里的 `content_type` 要按实际的填（`audio/pcm;rate=22050` 或 `rate=24000`），接口文档里的例子写的是 24000，不要写死。每块音频自己带着采样率（`Audio::sample_rate()`）。
6. **打断以后引擎要知道面试官那句话实际播到了哪里。** 语音线给出发现打断的时刻（`BargeInDetector::detected_at_ms()`）和候选人已经说的字；浏览器在 `playback` 消息里报播到了哪里。把这些填进 `TurnContext::interrupted`（哪一句、播了多少毫秒、全长多少毫秒），同一轮里每次调 `respond_with` 都要带上。
7. **回声。** 浏览器取麦克风时要打开回声消除（`getUserMedia` 的 `echoCancellation: true`），建议候选人戴耳机。`BargeInDetector::interviewer_says` 告诉它面试官正在说什么，漏进麦克风的同样的字不算打断，这是第二道保险，不是替代。
8. **一台 Mac 同时只能合成一句。** 模型一次跑一条，两场实时面试同时进行时现场合成会排队。实时模式先按一台 Mac 一场来用。

## 第一版先怎么做

候选人网页线定的第一版不走上面的实时通道，沿用逐题模式一句一句推进的 HTTP 协议：页面按静音判断候选人说完（阈值压到 2 秒左右），服务端用已经上传的录像分片转写，再调 `live::respond`，追问按句合成，一句一个完整的音频文件发给页面。好处是录制、断网重试、刷新续面都不用另做一套。`TurnListener` 和 `BargeInDetector` 留到下一步（语义判停和打断）再接。

候选人网页线在真的浏览器里量过这种做法（2026-11-13，云端容器，Chromium 加假麦克风循环放一段合成的回答，真识别模型，deepseek-flash，页面的静音阈值 2 秒；语音合成用的是瞬间完成的假后端）。两场各 10 到 11 轮，候选人说完最后一个字到面试官下一句开始播：

| | 中位数 | P95 |
| --- | ---: | ---: |
| 第一场 | 3.47 秒 | 3.85 秒 |
| 第二场 | 3.26 秒 | 3.79 秒 |

其中 2 秒是等静音，剩下一秒多是上传最后一片录像、转写和模型。服务端每轮的分段：拿到这段话的文字 0 到 0.4 秒（边传边识别，答完时基本已经有了），模型给出第一句可播的话 0.7 到 1.5 秒，整轮想完 0.8 到 1.8 秒。量的方法随第一版一起提交（#116），在 `crates/interview-room/README.md` 的「实时对话」和 `web/apps/candidate/README.md` 里。

这个数字不含真的语音合成。下一题的音频是提前合成的，所以就是上面的 3.3 到 3.5 秒。现场合成的追问要再加第一句的合成时间，这一段只在 Mac 上分开测过，加起来是估计：

| 这一轮面试官要说什么 | 候选人说完到听见 |
| --- | --- |
| 下一题（提前合成的） | 3.3 到 3.5 秒（实测） |
| 追问，IndexTTS 2，一句问句 | 约 7 秒（估计：上面的数字加一句 3.5 到 4 秒的合成） |
| 追问，IndexTTS 2，先接话再问 | 接话约 5 秒，问句约 9 秒（估计：两句排着队合成） |

这种做法下要注意两点：

- **一句一个完整文件时，BreezeTTS2 不占便宜。** 它快在第一块出得早，整句合成完反而比 IndexTTS 慢：一句追问 BreezeTTS2 要 5.15 秒，IndexTTS 2 是 3.95 秒，IndexTTS 2.5 是 3.26 秒。所以第一版里最快的是 IndexTTS 2.5，上面「实时模式用 BreezeTTS2」那一条要等音频能边合成边播才成立。
- **候选人说完时要把录像的最后一段马上交上来。** 录像默认 5 秒切一片，不主动交的话，最后几个字要等这一片录满才到服务端。

## 没有测和没有做的

- 实时通道下的第 5 段（网络和播放缓冲）没有测，要等候选人网页的实时通道做出来。第一版的做法在真浏览器里量过，见「第一版先怎么做」，但浏览器和服务端在同一台机器上，不含公网的延迟。
- 整条链路没有用真人的回答测过。声音是示例录音，交给引擎的文字是另外写的，两者对不上：真人说话时识别出来的错字、口头禅会不会让引擎判断错，没有测。引擎线自己用 29 个写出来的例子测过停顿和打断（87 次对 86 到 87 次），也不是真人录音。
- 真实麦克风和扬声器下的回声、背景噪音、口音，都没有测。
- 没有人听过三个引擎现场合成的追问。读出来的字用机器听写核对过（见 `tts/worker/README.md` 的「读出来的字对不对」），整句都对；很短的接话单独测过，IndexTTS 2 稳，纯语气词和 BreezeTTS2 克隆的「明白」不稳（见同一份文档的「很短的接话读得稳不稳」）。试听文件在 Mac 上。
- 上面整条链路的表是分别测了以后加起来的：识别和大模型在云端量，合成在 Mac 上量。三样放在一起的只跑过完整的实时对话面试（Mac 上，IndexTTS 2 克隆音色，见 `tts/worker/README.md` 的「接真引擎完整跑一场面试」）：候选人答完以后 2.4 到 3.5 秒听到面试官的第一句短话，和表里估的 3.5 秒对得上。那里的候选人是示例录音、答非所问，面试官每次都是先说一句「好的，咱们回到正题。」再说一句短问题，没有走到正常的追问。
- 上面合成的首块时间是用 Python 脚本直接调 worker 测的。后端的 `WorkerBackend` 连真 worker 也跑通了，数字对得上，见 `tts/worker/README.md` 的「用后端连真引擎走一遍」。

## 重现

```bash
# 整条链路（云端容器可以跑，读 DEEPSEEK_API_KEY，每遍不到一分钱）
eval "$(crates/interview-stt/scripts/fetch-sherpa-lib.sh)"
export AI_INTERVIEW_STT_MODEL_DIR=~/.cache/ai-interview/stt-models
INPUT=crates/interview-engine/fixtures/backend_engineer.json    # 出题用的输入；计划文件不存在时会先出题（约 0.1 元）
cargo run --release -p interview-stt --features sherpa --example realtime_latency -- 回答.wav $INPUT /tmp/plan.json --runs 10 \
    --answer "交给引擎的回答文字"
cargo run --release -p interview-stt --features sherpa --example realtime_latency -- 回答.wav $INPUT /tmp/plan.json --runs 10 \
    --answer "交给引擎的回答文字" --min-silence-ms 300

# 只测识别这一侧（不调大模型）
cargo test --release -p interview-stt --features sherpa --test sherpa_live -- --ignored --nocapture --test-threads=1
```

`回答.wav` 用任意一段中文录音。上面的数字用的是识别模型自带的四段示例录音接在一起，每段之间隔 0.25 秒，共 30 秒。不带 `--answer` 时交给引擎的就是识别出来的文字。语音合成的测法见 `tts/worker/README.md`。
