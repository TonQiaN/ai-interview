# TTS worker

三个 TTS 引擎只能在 Apple Silicon 的 Mac 上推理，后端是 Rust 写的、通常跑在别的机器上。worker 是 Mac 上的一个常驻 Python 进程：模型加载一次留在内存里，后端通过 HTTP 让它合成。

- `worker.py`：HTTP 服务，只用标准库，两个引擎的 Python 环境都能直接跑。
- `engine_indextts.py`、`engine_breeze.py`：三个真引擎的适配。2026-11-13 在 M3 Max 上用真模型验证过：克隆、Breeze 文字设计音色、IndexTTS 情绪、流式输出、出错处理。实测数字见下面「真引擎的行为和实测」。
- `engine_fake.py`：`--fake` 时用的假引擎，不加载模型，输出测试音，用来在任何机器上测协议。

Rust 那边对应的是 `crates/interview-tts` 的 `WorkerBackend`。

## 启动

IndexTTS 和 Breeze 的依赖不能装进同一个环境（见 [../README.md](../README.md) 的「已知的坑」），所以起两个进程，各占一个端口：

```bash
REPO=~/Desktop/ai-interview    # 仓库在 Mac 上的位置，vendor/ 和 models/ 都在它下面

cd $REPO/vendor/mlx-indextts2 && .venv/bin/python $REPO/tts/worker/worker.py --engines index2,index25 --port 7801 --preload
cd $REPO/vendor/breeze-tts-mlx && .venv/bin/python $REPO/tts/worker/worker.py --engines breeze2 --port 7802 --preload
```

后端这边告诉它 worker 在哪：

```bash
AI_INTERVIEW_TTS_BACKEND=worker
AI_INTERVIEW_TTS_WORKER_URLS=http://127.0.0.1:7801,http://127.0.0.1:7802
AI_INTERVIEW_TTS_WORKER_TOKEN=<两边一致的随机串>     # worker 不在本机时必填
AI_INTERVIEW_TTS_LIVE_DIFFUSION_STEPS=16             # 可选：实时对话现场合成的句子少走几步，见「IndexTTS 2 每段的用时花在哪」
```

后端启动时问每个 worker 它有哪些引擎，之后按引擎把请求发给对应的 worker。

参数：

| 参数 | 含义 |
| --- | --- |
| `--engines` | 这个进程提供哪些引擎，逗号分隔：`index2,index25` 或 `breeze2` |
| `--fake` | 不加载模型，输出测试音。见下面「不用 Mac 也能测」 |
| `--port`、`--host` | 监听的端口和地址，默认 `127.0.0.1:7801`。端口填 0 由系统挑，实际端口打印在标准输出的第一行（`listening <端口>`）。监听本机以外的地址时必须设令牌 |
| `--models` | 权重目录，默认是仓库下的 `models/` |
| `--state` | 存参考录音的目录，默认是仓库下的 `.runtime/tts-worker/` |
| `--preload` | 启动时就加载模型。不加的话第一条请求会多等几秒。IndexTTS 的两个版本内存里只留一个，预加载完留下的是 `--engines` 里排第一的 |
| `--memory-limit-gb` | IndexTTS 的内存上限，默认 28 |
| `--cache-limit-gb` | IndexTTS 用的 MLX 缓存上限，默认 2。见「加载和内存」 |

IndexTTS 2 和 2.5 在同一个进程里，内存里一次只留一个版本，切换时重新加载：切换后的第一条请求实测多花 1.3 到 2.4 秒。

## 协议

版本 1。请求和错误都是 JSON，字段用 `snake_case`。设了令牌时每个请求都要带 `Authorization: Bearer <令牌>`。

### `GET /v1/health`

```json
{
  "worker": "ai-interview-tts",
  "protocol": 1,
  "busy": false,
  "engines": [
    {"engine": "index2", "ready": true, "loaded": true, "detail": "IndexTTS-2-mlx-8bit"}
  ]
}
```

`ready` 是权重在不在，`loaded` 是模型现在是不是已经在内存里，`busy` 是此刻是不是正在合成。

### `HEAD /v1/references/{sha256}` 和 `PUT /v1/references/{sha256}`

克隆音色的参考录音按内容的 SHA-256 存在 worker 本机。后端合成前先 `HEAD` 问有没有（200 有，404 没有），没有就 `PUT` 上传（请求体是 WAV 文件，不超过 20 MB，成功返回 204）。worker 会核对内容和地址里的哈希是否一致。

参考录音是真人的声音，只存在 worker 的 `--state` 目录里，不进 Git。

### `POST /v1/synthesize`

```json
{
  "engine": "index2",
  "text": "请先做一个简单的自我介绍。",
  "language": "zh",
  "voice": {"kind": "clone", "reference_sha256": "<64 位十六进制>", "transcript": "<参考录音的逐字稿，Breeze 必填>"},
  "style": {"emotion": "calm", "emotion_strength": 0.65, "instruction": "<导演指令，只有 Breeze 用>"},
  "seed": 42,
  "diffusion_steps": 16,
  "stream": false
}
```

- `diffusion_steps` 可以不给。它是 IndexTTS 声学生成走几步，4 到 50 的整数，不给是 25；BreezeTTS2 忽略它。后端只在实时对话现场合成时带这个字段（设了 `AI_INTERVIEW_TTS_LIVE_DIFFUSION_STEPS` 才带），预先合成的题目不带。加这个字段之前的 worker 会直接忽略它，所以后端和 worker 要一起更新。
- `voice` 也可以是 `{"kind": "design", "description": "温和的女声"}`，只有 BreezeTTS2 支持。
- `style` 整个可以不给。`emotion` 不给就是自然语气。
- 文本的长度限制由后端在发请求前检查和分段，worker 不再切。

返回：

- `stream` 为 `false`：`audio/wav`，16 位单声道，整段合成完才返回。
- 采样率跟着引擎走：IndexTTS 两个版本是 22.05 kHz，BreezeTTS2 是 24 kHz。调用方不能写死，要读 WAV 头或 `X-Sample-Rate`。
- `stream` 为 `true`：`application/octet-stream`，分块传输的 PCM16 小端单声道裸数据，采样率在响应头 `X-Sample-Rate` 里。引擎生成一块发一块，后端可以边收边播。合成中途出错时 worker 直接断开连接（响应头已经发出去，没法再回错误），后端要把没收完的流当作失败。

模型一次只跑一条请求，同时来的请求排队。

流式合成到一半调用方断开连接（比如实时对话里候选人打断了面试官），worker 停止生成这一条，不算出错。BreezeTTS2 约 0.4 秒就停；IndexTTS 一段生成到一半停不下来，要等当前这段算完（实测 3 到 7 秒），这期间下一条请求在排队。

### 错误

```json
{"error": {"code": "reference_missing", "message": "这段参考录音还没上传到 worker"}}
```

| 状态码 | `code` | 含义 |
| --- | --- | --- |
| 400 | `invalid_request` | 请求不对，`message` 里说哪里不对。引擎自己发现的问题也算：IndexTTS 没给参考录音、不认识的情绪、BreezeTTS2 克隆不带逐字稿 |
| 401 | `unauthorized` | 令牌不对 |
| 404 | `not_found` | 没有这个接口 |
| 409 | `reference_missing` | 参考录音还没上传，先 `PUT` 再重试 |
| 413 | `payload_too_large` | 请求体太大 |
| 500 | `synthesis_failed` | 引擎合成失败，细节在 worker 的日志里 |
| 500 | `internal` | worker 自己出错 |
| 503 | `engine_unavailable` | 这个 worker 不提供请求的引擎 |

## 真引擎的行为和实测

2026-11-13 在 M3 Max、64 GB 的 Mac 上测的，测试脚本和 worker 在同一台机器上，不含网络。测的时候机器不是空闲的（系统负载 5 左右），IndexTTS 的数字受影响明显：另一轮里 IndexTTS 2 的长段总耗时中位数是 22.9 秒而不是下表的 17.8 秒。BreezeTTS2 两轮几乎一样。

### 能不能边生成边出

| 引擎 | 流式 | 说明 |
| --- | --- | --- |
| `index2` | 按段出 | 长文本先用模型的分词器切段（每段最多 100 个文本 token），生成完一段交一段。段内不是流式。一两句话只有一段，首块就是整句 |
| `index25` | 按段出 | 同上，每段最多 40 个文本 token，所以长文本的首块更早 |
| `breeze2` | 真流式 | 模型每生成几帧就解码出一块，约 160 毫秒一块 |

三个引擎流式拼起来的音频都和整段返回的逐字节一样。IndexTTS 2 的适配代码没有分段输出的入口，这里是先切好段再一段一段生成，结果和上游整段生成逐字节一样。

### 首块和总耗时

每句热身一次后跑三次，取中位数，单位秒。首块是从发出请求到收到第一块音频。实时率是总耗时除以音频时长，小于 1 表示比实时快。四句话从短到长：两个字的应答、一句追问、两三句话、一段长的开场白。

| 配置 | 句子 | 首块 | 总耗时 | 音频时长 | 实时率 |
| --- | --- | ---: | ---: | ---: | ---: |
| IndexTTS 2 克隆 | 两个字 | 1.44 | 1.44 | 0.95 | 1.52 |
| IndexTTS 2 克隆 | 一句 | 3.95 | 3.95 | 5.69 | 0.69 |
| IndexTTS 2 克隆 | 两三句 | 4.54 | 8.10 | 11.59 | 0.70 |
| IndexTTS 2 克隆 | 长段 | 5.78 | 17.79 | 26.37 | 0.68 |
| IndexTTS 2.5 克隆 | 两个字 | 1.41 | 1.41 | 1.11 | 1.26 |
| IndexTTS 2.5 克隆 | 一句 | 3.26 | 3.26 | 5.63 | 0.58 |
| IndexTTS 2.5 克隆 | 两三句 | 3.72 | 6.71 | 11.48 | 0.58 |
| IndexTTS 2.5 克隆 | 长段 | 2.31 | 16.14 | 24.90 | 0.65 |
| BreezeTTS2 克隆 | 两个字 | 0.21 | 0.57 | 0.64 | 0.90 |
| BreezeTTS2 克隆 | 一句 | 0.23 | 5.15 | 6.80 | 0.76 |
| BreezeTTS2 克隆 | 两三句 | 0.23 | 9.43 | 12.56 | 0.75 |
| BreezeTTS2 克隆 | 长段 | 0.27 | 20.59 | 27.52 | 0.75 |
| BreezeTTS2 设计音色 | 两个字 | 0.16 | 1.19 | 1.52 | 0.78 |
| BreezeTTS2 设计音色 | 一句 | 0.18 | 5.09 | 6.72 | 0.76 |
| BreezeTTS2 设计音色 | 两三句 | 0.19 | 7.93 | 10.48 | 0.76 |
| BreezeTTS2 设计音色 | 长段 | 0.23 | 19.96 | 26.32 | 0.76 |

三次里的最大值比中位数最多高 5%。

怎么读这张表：

- IndexTTS 每条请求有约 1.4 秒的固定开销，再加上整段的生成时间。一句 6 秒的追问要等 3.3 到 4 秒才有第一个音。
- BreezeTTS2 的首块稳定在 0.2 秒上下，和句子长短无关。它生成得比实时快（实时率 0.75），所以可以边收边播不卡。
- 把一句追问在逗号处切成两半分别合成，IndexTTS 的前半句 1.9 到 2.7 秒合成完，比整句早 1.3 到 1.7 秒，代价是两半接起来比整句长 1.1 秒左右（中间多了停顿）。语调接不接得上还没有人听过。

### 加载和内存

- 带 `--preload` 启动：IndexTTS 的 worker 7.5 到 9.7 秒（两个版本各加载一次，含参考编码器），BreezeTTS2 的 worker 5.2 到 8.5 秒。
- IndexTTS 的 worker 加载完占 3.7 GB，合成起来稳定在 7 到 11 GB，峰值 12 GB，不随合成的条数涨：一个 worker 不重启连着合成 88 条（两个版本都用过，中间跑了一场完整的面试），停之前是 8.9 GB。BreezeTTS2 的 worker 加载完 4 GB，用起来 7 到 8 GB。两个 worker 同时常驻约 17 GB。这里说的是 `footprint` 报的实际占用（含显存），`ps` 里的 RSS 小得多。
- IndexTTS 早先占 22 到 33 GB，原因有两个，worker 里都处理了：
  - 适配代码加载时用 `mx.compile` 编译了声码器，编译结果按输入的形状缓存。每段音频的长度都不一样，所以每合成一段就多留约 0.42 GB，不会释放，也清不掉。合成五六十段以后 MLX 在用的内存越过 `--memory-limit-gb`：不报错，但合成慢一倍（实时率从 0.7 变成 1.5），并且接着涨，69 条后进程占到 44 GB。一场面试要合成三四十段，也就是连着服务两场就会变慢。worker 现在不让它编译：IndexTTS 2 的 30 段输出和编译时逐字节相同，速度相差不到 3%（形状几乎每段都是新的，编译本来就帮不上忙）；IndexTTS 2.5 走同一个方法，占用同样稳定，同样的请求发两遍输出逐字节相同。
  - 适配代码把 MLX 的缓存上限设成机器内存的四分之一（64 GB 的机器是 16 GB），第一条请求就填满。worker 加载后改成 `--cache-limit-gb`（默认 2），速度不受影响。
- `--memory-limit-gb` 不是硬上限，越过以后 MLX 照样分配。worker 在每条请求之后看一眼 MLX 在用的内存，超过上限的八成就在日志里提醒（正常是 3 GB 上下）。见到这条提醒就重启 worker，并且查一下是不是适配代码升级后编译又回来了。
- 参考编码器的几个 PyTorch 模块在显存里常驻 2.4 GB，算在上面的数字里。

### 读出来的字对不对

2026-11-13 用 Mac 上已有的 Whisper large-v3-turbo（`mlx-whisper`，研究阶段评测错字率用的同一套）把合成出来的音频听写了一遍，和原文比（去掉标点、繁体转简体后算编辑距离）。没有整句读错、漏句或者重复读的。

| 哪一批 | 文件数 | 字数 | 不一致 | 不一致在哪 |
| --- | ---: | ---: | ---: | --- |
| 后端连真引擎那一遍的输出（一句问候、一句提问、一句追问） | 13 | 226 | 4 | IndexTTS 2 和 BreezeTTS2 带情绪或导演指令的问候各一处「你好」听成「您好」；BreezeTTS2 克隆把「最近」听成「最新」、多听出一个「的」 |
| 首块测量时的四句话，两三句和一句的（31 字、60 字） | 8 | 364 | 1 | IndexTTS 2.5 的「扛住」听成「扛出」 |
| 同上，长段（123 字） | 4 | 492 | 2 | IndexTTS 2 和 2.5 都把结尾的「降级」听成「降低」。「一千万」听写成「1000万」不算 |
| 同上，两个字的应答「明白。」 | 4 | 8 | 2 个文件 | BreezeTTS2 克隆和 IndexTTS 2.5 的这一条听写出来完全不对。不到一秒的音频识别本来就不稳，也可能是读得不清楚 |

这些不一致是合成读错了还是识别听错了，机器分不出来，要人听。值得听的：BreezeTTS2 克隆的提问和追问、两个 IndexTTS 长段的结尾、两个字的应答。文件在 Mac 的 `data/worker-live/` 和 `data/worker-eval/` 下（不进 Git）。

### 很短的接话读得稳不稳

实时对话里面试官接话用的正是很短的句子，上表最后一行又显示两个字的应答可能有问题，所以 2026-11-13 单独测了一遍：12 句接话（两个字的、四五个字的、一个短句的各 4 句），每个引擎每句用三个随机种子各合成一次，一共 108 段，都克隆 R001，用同一套 Whisper 听写。

下表是「实质不一致」的段数：「得」听写成「的」、句首的「嗯」被省掉这两类明显属于识别的差别不算。

| 引擎 | 两个字（12 段） | 四五个字（12 段） | 一个短句（12 段） | 合计（36 段） |
| --- | ---: | ---: | ---: | ---: |
| IndexTTS 2 | 2 | 0 | 0 | 2 |
| IndexTTS 2.5 | 3 | 1 | 1 | 5 |
| BreezeTTS2 | 4 | 3 | 6 | 13 |

- **IndexTTS 2 的短接话能用。**「明白。」「好的。」「了解。」9 段全部听写正确，四五个字和短句的 24 段没有实质错误。不一致的 2 段都是「嗯嗯。」。
- **「嗯嗯。」这种纯语气词不要用。** 两个 IndexTTS 版本一共错了 3 段，Whisper 听语气词本来也不准，机器判断不了。
- **IndexTTS 2.5 比 IndexTTS 2 差一些。** 5 段不一致分散在不同的句子和种子上，没有哪一句三个种子都错。另有一段「明白，谢谢。」比同一句的其他几段长了近一倍，结尾没有静音，可能多读出了东西。
- **BreezeTTS2 克隆读「明白」不稳，和句子长短无关。**「明白。」三个种子全错；含「明白」的 12 段里，「明白」听写对的只有 4 段（IndexTTS 2 是 12 段，IndexTTS 2.5 是 10 段）。句子变长也没有变稳。「好，这一点我记下了。」三个种子都听成「记一下了」，两个 IndexTTS 版本这句 6 段全对，像是真的多读了一个字。之前用文字设计的音色读「明白。」是对的，所以问题可能出在克隆模式上，设计音色这次没测。
- **更像是合成的问题，不是识别的问题。** 同一套 Whisper 把 IndexTTS 2 那些有声部分只有 0.3 到 0.7 秒的应答全听对了；每段前后各垫半秒静音再听一遍，错的还是那些段。
- 没有发现被截断的。IndexTTS 的音频开头有 0.16 到 0.27 秒的静音，BreezeTTS2 几乎没有。

顺带量到的等待时间（从发请求算起的中位数，秒；当时机器上还有别的负载）：

| 引擎 | 两个字 | 四五个字 | 一个短句 |
| --- | ---: | ---: | ---: |
| IndexTTS 2，合成完 | 1.60 | 2.03 | 2.23 |
| IndexTTS 2.5，合成完 | 1.51 | 1.80 | 2.06 |
| BreezeTTS2，第一块 / 合成完 | 0.21 / 0.88 | 0.22 / 1.08 | 0.22 / 1.35 |

音频在 Mac 的 `data/worker-acks/` 下（不进 Git），文件名是 `引擎-组和句号-s种子.wav`（a 是两个字的，b 是四五个字的，c 是短句）。值得听的：`breeze2-a1-s42.wav`、`breeze2-a1-s43.wav`、`breeze2-c2-s42.wav`（「明白」）、`breeze2-c4-s43.wav`（「记下了」）、`index25-b4-s43.wav`（结尾），对照 `index2-a1-s42.wav`。

### 固定的接话：十六句读得稳不稳、每句多长

上面那两场实时对话之后，引擎线把面试官现场开口的第一句改成只从一份固定清单里选（`interview_engine::openers`，中英文各八句），面试间在面试开始时把它们提前合成好。2026-11-13 把这十六句在四种引擎音色下各合成 3 遍（种子 42、43、44），一共 192 段，全部合成成功，英文句子三个引擎都能读。听写用同一套 Whisper，英文转小写、去标点后逐词比。

听写完全一致的遍数：

| 引擎音色 | 中文（24 遍） | 英文（24 遍） | 中文时长中位 | 英文时长中位 | 中文合成用时中位 |
| --- | ---: | ---: | ---: | ---: | ---: |
| IndexTTS 2 克隆 | 23 | 20 | 1.92 | 2.46 | 1.97 |
| IndexTTS 2.5 克隆 | 19 | 21 | 2.15 | 2.57 | 1.86 |
| BreezeTTS2 克隆 | 17 | 19 | 1.56 | 1.48 | 1.13 |

IndexTTS 2 下每句的音频时长（3 遍的中位，秒），首尾各带 0.15 到 0.25 秒静音：

### IndexTTS 2 每段的用时花在哪，步数少一点能省多少

上面说合成一句大约是 1.0 秒加每个字 0.09 秒。2026-11-13 在 Mac 上把这 1 秒拆开计时（模型已预热，同一段 6.8 秒的参考录音，种子 42，单位秒）：

| 要说的话 | GPT 自回归 | 声学生成 | 声码器 | 合计 | 音频时长 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 3 个字 | 0.14 | 0.96 | 0.10 | 1.23 | 0.64 |
| 10 个字 | 0.42 | 1.10 | 0.34 | 1.88 | 2.00 |
| 17 个字 | 0.69 | 1.24 | 0.54 | 2.50 | 3.20 |
| 25 个字 | 1.15 | 1.58 | 0.80 | 3.59 | 5.09 |

- **固定的那 1 秒在声学生成（flow matching）这一步。** 它每次都把整段参考录音（6.8 秒是 585 帧）和新生成的帧一起算，走 25 步，每步过两遍模型（带条件和不带条件各一遍）。所以只说一个「好的」也要 1 秒，和要说的话多长关系不大。换个说法：合成用时约等于 0.9 秒加 0.5 乘音频秒数。
- 参考录音的预处理（提特征、算说话人向量）适配代码按文件路径缓存，worker 把参考录音存在固定路径上，所以每次都命中，没有重复算。没命中时多花约 0.7 秒，只出现在 worker 启动后的第一条请求和切换 IndexTTS 版本之后。
- 除了步数没有别的浪费。worker 写死的 25 步是上游 PyTorch 版的默认值（MLX 适配代码自己的默认是 16）。

少走几步，同样四句话的合计用时：

| 步数 | 3 个字 | 10 个字 | 17 个字 | 25 个字 | 和 25 步比的频谱差 | 峰值 |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| 25（默认） | 1.23 | 1.88 | 2.50 | 3.59 | | 0.92 |
| 16 | 0.87 | 1.54 | 2.12 | 2.99 | 1.4 到 3.0 dB | 0.95 |
| 12 | 0.76 | 1.42 | 1.95 | 2.76 | 2.3 到 4.1 dB | 0.99 |
| 10 | 0.66 | 1.28 | 1.80 | 2.64 | | 0.99 |

- 16 步每段省 0.35 到 0.6 秒，12 步省 0.5 到 0.8 秒（经 worker 的 HTTP 接口量是 0.51 到 0.82 秒）。
- 步数变了，时长不变，听写全对，同一个步数下结果可以复现；但波形和 25 步不一样，12 步以下峰值顶到了削波上限 0.99。**音质有没有变差要人听，机器只能说差了多少。** 三档的录音在 Mac 的 `data/worker-profile/` 下，文件名是 `index2-steps步数-字数.wav`。
- 内存不随步数变。
- 所以做成了可配置：后端设 `AI_INTERVIEW_TTS_LIVE_DIFFUSION_STEPS` 以后，实时对话里现场合成的句子（包括面试开始时提前合成的固定接话）用这个步数，预先合成的题目还是 25 步。步数进缓存键，两种不会互相拿错。**默认不设，用几步等人听过再定。**
- 没有试的：把参考录音截短（每短 1 秒省约 0.13 秒，但克隆的依据变了，音色要重新确认）；关掉不带条件的那一遍（声学生成快一倍，音质会受影响）。

并发也顺带量了：一个 worker 严格排队，第二条请求要等前一条剩下的时间。同时起两个 IndexTTS 进程并行合成两句，两句都要到 4.2 秒才完成；排队时第二句到 5.1 秒完成，但第一句不受影响。实时对话要的是第一句早出来，所以排队更合适。多起一个 IndexTTS 进程要多占约 9 GB 内存。

### 还没验证的

- 没有人听过。上面都只是机器听写，音色像不像、语气自不自然、有没有杂音，听写看不出来。
- BreezeTTS2 克隆读不稳「明白」是不是只在 R001 这个音色上出现，换一段参考录音会不会好，没有测。
- IndexTTS 2.5 少走几步省多少、听起来怎么样没有量，上面的数都是 IndexTTS 2 的。
- IndexTTS 2 读多音字和夹在中文里的英文词不稳：「去重」的「重」像是读成了 zhòng，PostgreSQL 读不准。要不要让引擎在这类词上换说法，没有定。
- 多场面试同时进行时排队会排多久，没有测。

### 实现上要知道的

- 所有碰模型的操作都在一个固定的线程里做（`ModelThread`）。MLX 的计算流跟着线程走，HTTP 服务每个请求开一个新线程，模型换一个线程用会报 `There is no Stream(...) in current thread`。
- IndexTTS 的参考编码器在加载模型时就加载并检查。适配代码发现权重加载失败只打印一次、之后照常生成，所以 worker 一直记着这个状态，`/v1/health` 里这个引擎会变成 `ready: false`，合成请求返回 500。
- IndexTTS 一段生成到 token 上限被截断时，worker 记一条警告，这段的结尾可能不完整。
- BreezeTTS2 的适配代码没有装进它的环境，只是放在 `vendor/breeze-tts-mlx` 目录下，worker 启动时把这个目录加进 Python 的搜索路径。
- BreezeTTS2 的日志里会出现 `Residual tail decode detected`，是适配代码在最后一块帧数不满时自己打的，不影响输出。

## 用后端连真引擎走一遍

`AI_INTERVIEW_TTS_LIVE_ENGINES=index2,breeze2` 只测其中几个引擎。`AI_INTERVIEW_TTS_LIVE_OUT_DIR=目录` 把合成出来的音频存成 WAV 方便人听；克隆出来的是真人的声音，这个目录要放在不进 Git 的地方（比如 `data/` 下）。测试只打印时间、时长和采样率，不打印逐字稿。

| 引擎 | 整段（一句问候） | 流式（一句提问）第一块 / 全部 | 打断后的下一句 | 情绪或导演指令 | 设计音色 |

- worker 刚起来的第一条请求偏慢（第一遍 IndexTTS 2 整段 3.56 秒，BreezeTTS2 整段 3.42 秒）。
- 测的时候机器不是空闲的，系统负载 5 上下。

| 现场合成最长的一段 | 3.31 | 2.83 |
| 候选人答完到听到第一声，最长 | 3.4 | 3.1 |
| IndexTTS 进程的内存 | 3.7 到 11.0 GB | 3.7 到 11.0 GB |

候选人答完到听到第一声，分三种情况：

| 第一句是怎么来的 | 等多久 |
| --- | ---: |
| 现场合成 | 2.2 到 3.4 |
| 预合成的过渡语，或者合成缓存里已经有的接话 | 1.1 到 1.6 |
| 不用面试官说话的步骤 | 0 到 0.4 |

第二种情况里等的只有大模型判断的那一段：从模型决定好到第一句可以播，命中缓存时是 0.2 到 0.5 秒，要现场合成时是 1.9 到 2.3 秒。测试打印的「等下一步」每一段话算一步，一轮里第二段的等待也在里面（第二场最长的 3.7 秒就是一段问句的合成加排队），测试不会真的把上一段播完，所以它不等于候选人听到的空白，空白在下面单算。

第一声之后还有一段空白：接话播完，问句还没合成好，候选人干等。一轮里的几段是一段合成完再合成下一段的，所以空白等于问句的合成用时减去接话的音频时长。两场里每一轮的空白：

| 第一句 | 第一句的音频 | 第一句播完到问句开始 |
| --- | ---: | ---: |
| 好的。 | 0.64 | 2.70、2.16 |
| 明白。 | 0.95 | 2.76（其中 1.15 是排队）、1.82、1.64、1.61、约 1.2 |
| 这个我记下了。 | 1.21 | 1.70 |
| 好的，我再说一遍。 | 1.70 | 0.67 |
| 好的重申一下。 | 1.89 | 0.46 |
| 好的，咱们回到正题。 | 2.00 | 0.64、0.88、0.74 |

- 接话越短，后面空得越久。问句十几二十个字，IndexTTS 2 要 2.2 到 3.3 秒才合成完，「好的。」「明白。」盖不住。
- 提前把「明白。」「好的。」合成好，第一声早出来约 1.5 秒，问句也跟着早开始：候选人答完到问句开始，接话命中缓存的四轮是 3.6 到 4.2 秒，接话要现场合成的是 5.1 到 6.2 秒。但接话播完以后的空白没有变短，还是 1.6 到 2.2 秒。要把空白也去掉，第一句得是两秒左右、而且提前合成好的：按这两场的数字，那样第一声 1.1 到 1.6 秒，之后空白不到 1 秒。这个建议已经给了引擎线和面试间线。
- 第二场里提前合成没赶上第一轮：面试开始以后先等了 5.4 秒数据库连接，再用 3.9 秒合成两句，而测试里的候选人不等开场白播完就答完了，第一轮在 5.6 秒时就来了，自己又合成了一遍「明白。」。两边在 worker 上排了队，第一轮的问句因此多等 1.15 秒。等连接是当时的测试自己造成的（面试开始以后测试同步跑 ffmpeg 生成录像，占住了唯一的线程），后来测试改成先生成录像再开始面试（PR #167）；服务进程是多线程的，不受影响。真的面试光开场白就有二十多秒，赶得上。
- 长句在逗号处断开的只出现一次（第一场）：前半句 22 个字、音频 4.19 秒，后半句 13 个字、合成 2.27 秒，后半句在前半句播完之前 1.86 秒就备好了，接得上。前半句结尾的静音 0.16 秒，和普通句子一样，没有被截断。语调像不像话没说完，一个样本说不准，要人听。
- 机器听写现场合成的 27 段，16 段完全一致。不一致的多数是同音字（「云帆」「队列」「幂等」）。有一段要人听：32 个字、带 PostgreSQL 的一句，音频只有 4.2 秒，开头六个字和 PostgreSQL 都没听写出来，IndexTTS 2 读夹在中文里的英文词可能不行。还有一段结尾没有留静音，最后 20 毫秒还有声音，字都在，但收得很紧。
- 文件在 Mac 的 `data/worker-live-e2e/run5/` 和 `run6/`。第二场是用 `AI_INTERVIEW_LIVE_KEEP_AUDIO_DIR` 留下来的。
- 测试默认不输出后端的日志。想看每一轮的 `first_ready_ms`（第一句多久可以播）、`settled_ms`（这一轮的话都备好了）和 `synth_ms`（这一轮现场合成一共多久），设 `AI_INTERVIEW_LOG=info`。

### 接话换成固定清单以后的两场，25 步和 16 步各一场

引擎线把现场开口的第一句改成只从固定清单里选，面试间在面试开始时把清单里的八句提前合成好（PR #169、#174）。之后又跑了两场，做法和上面两场一样（IndexTTS 2 克隆音色，四道题，同样三段合成的回答）。两场只差一个环境变量：第二场设了 `AI_INTERVIEW_TTS_LIVE_DIFFUSION_STEPS=16`（见「IndexTTS 2 每段的用时花在哪」）。都通过，没有让页面重试，没有合成超时，没有退回只出文字，worker 日志里没有警告。单位秒：

| | 25 步（默认） | 现场 16 步 |
| --- | ---: | ---: |
| 出题加预合成 | 156.2 | 159.5 |
| 预合成的句数 / 音频总时长 / 合成用时 | 16 句 / 109.7 / 80.6 | 16 句 / 116.5 / 81.2 |
| 面试本身 | 19 步，34.1 | 15 步，22.0 |
| 整场 | 293 | 285 |
| 大模型花费 | 0.57 元 | 0.58 元 |

第二场面试官问到第 3 题就结束了（第一场问了 4 题），开口说话的是 4 轮对 5 轮，问句的文字也不一样，逐轮的数只能大致比。

- **接话全部来自清单。** 两场开口说话的九轮，第一句都是清单里的句子，没有一轮要现场另写。除了每场的第一轮，都命中缓存：从模型决定好到第一句可以播是 0.07 到 0.55 秒。
- **接话现成以后，候选人答完约 1 秒听到第一声**，等的只剩大模型判断的那一段。
- **接话后的空白，不排队时 25 步是 0.4 到 1.3 秒，16 步是 0.7 秒以内**，有一轮问句比接话先备好。
- **提前合成和现场的问句抢同一个 worker。** 模型一次只跑一条，严格排队。这两场里测试的候选人不等开场白播完就答完，第一轮在面试开始后 0.2 秒就来了，八句还没合成完，后面几轮的问句排在提前合成的句子后面：25 步那场多等 0.65 到 2.30 秒，16 步那场多等 0.15 到 1.27 秒。实际量到的空白比上一行多出来的部分全是排队。真的面试里开场白加第一题有三十多秒，八句十五六秒就合成完，一般碰不上；候选人一上来就打断或很快答完时会碰上。要不要让现场的句子插队由面试间线定。
- **16 步确实生效，预合成没受影响。** worker 日志不记这个字段，是重放验证的：同样的文字、参考录音和种子，按 25 步和 16 步各合成一遍，和两场留下的音频逐字节比。现场的句子（含提前合成的接话）第一场和 25 步的相同、第二场和 16 步的相同；预合成的题目两场都和 25 步的相同。不给这个字段和给 25 的输出也逐字节相同。
- **16 步每句省 0.5 到 0.7 秒。** 文字完全相同的七句接话每句省 0.51 到 0.63 秒；字数相近的问句省 0.7 秒上下。粗略地说，16 步是 0.7 秒加每个字 0.07 秒，25 步是 1.2 秒加每个字 0.08 秒。
- **机器听写没有发现 16 步读得更差。** 16 步那场现场的 8 段：四段接话全对，结尾都有静音，峰值 0.59 到 0.93，没有顶到削波上限。问句里「去重」两次都被听成别的（像是把「重」读成了 zhòng），PostgreSQL 两场都读不准，这两样和步数无关。**音质还是要人听。**
- 文字相同、可以对着听的三对（前一个 25 步，后一个 16 步），都在 Mac 的 `data/worker-live-e2e/` 下：`run7/q1.r1.s1.wav` 对 `run8/q1.r1.s1.wav`，`run7/q2.p1.s1.wav` 对 `run8/q2.p1.s1.wav`，`run7/q2.p2.s1.wav` 对 `run8/q2.p2.s1.wav`。更长的句子见 `data/worker-profile/`。
